---

## 0 · 一句话结论

把 aiworkgate 从「自带 12 个 Go 插件的网关」重构为「**能安装/加载/更新 magpie 生态（OpenCode 格式）插件的公网网关**」：
本机负责登录，服务器（租用）负责 7×24 服务，凭据加密同步，客户端用 Key + 期限分享给他人。

## 2 · 目标架构

```
┌─ 本机（Windows，登录机，可关机）──────────────┐
│  magpie（现有，不改动）                        │
│    └─ 登录各渠道 → plugin-auth.json            │
│  aiworkgate（重构后）                          │
│    ├─ 同步器：读 magpie 凭据 → 加密推送服务器   │
│    └─ 插件宿主桥（bun 单文件）                 │
│        └─ 加载 opencode-*.auth 插件（本机自用）│
└───────────────┬──────────────────────────────┘
                │ HTTPS 推送（服务器公钥加密）
                ▼
┌─ 服务器（租用，Linux，7×24）──────────────────┐
│  Caddy（TLS 自动续期 + IP 限流）               │
│    └─ 反代 → 127.0.0.1:17865                  │
│  aiworkgate                                   │
│    ├─ 公网鉴权：agk_ Key（expires_at 等）      │
│    ├─ 服务开关：正常/暂停/白名单               │
│    ├─ 协议：chat/completions/responses/       │
│    │        messages/gemini（5 选 4）          │
│    ├─ 插件宿主桥（同本机，同一个 exe）         │
│    │    └─ 加载同样的 .mjs 插件                │
│    └─ 凭据库：加密存储 + 续期 + 吊销           │
│         └─ access 过期→自动 refresh（不需本机）│
└───────────────┬──────────────────────────────┘
                ▲
           手机 / 朋友的设备（Key + 期限）
```

**双机同一份桥**：本机与服务器跑同一个插件宿主桥 exe，差别只在「凭据来源」：
本机桥可触发浏览器登录；服务器桥只消费同步来的凭据、只做 refresh 续期。

### P5 · 公网化（Key 扩展 + 开关 + 反代）

> **限流四件套与价格倍率的字段级规格见 [`2026-11-05-供应商配置面板字段规格.md`](./2026-11-05-供应商配置面板字段规格.md) §图三**：
> 并发上限（超出排队而非拒）/ 每分钟请求数（重试计入、等空位最多 2 分钟）/ 排队上限（超出立刻拒）/ 排队等待（0=一直等）/ 价格倍率（模型级不被覆盖）。
> **11~15 项不做 = 一个 Key 就能打穿所有渠道或无限排队**。

**做什么**
1. Key 扩展（F-08）：`client_keys` 加列 `expires_at INTEGER`、`max_requests_total INTEGER`（0=不限）、可选 `allowed_ips TEXT`；DDL 走既有 migration 惯例；**分享 Key 创建时到期必填**
2. 校验链 fail-closed（F-09 修复，审计 P1-9）：store 读错误时拒绝请求而非放行
3. 服务开关三态（D-11）：`service_mode: open|paused|whitelist`；paused 对一切 `/v1/*` 返回 503 + 明确文案；whitelist 只放行 Key 属主标记为 owner 的请求
4. 反代信任：新增 `trusted_proxies` 配置；仅信任列表内来源的 `X-Forwarded-For`，否则按直连 IP 处理；`allowedRequestHost` 放行反代场景
5. IP 限流：网关侧每 Key + 每 IP 双维滑动窗口（简单实现，够用即可）；重火力防护交给反代（Caddy `rate_limit`/fail2ban）
6. 部署产物：服务器 Linux 版构建（`CGO_ENABLED=0` 已具备）；Caddy 配置样例（域名、自动证书、反代到 127.0.0.1:17865）
7. **凭据异常审计**：`last_used_at` 落库 + 管理页可见；后续可加「非活跃时段调用」告警（用户已认可方向，本期先落数据）

**验收**
- [ ] 过期 Key 请求 → 401 + 明确文案；`expires_at=null` 的自有 Key 不受影响
- [ ] `paused` 模式下手机请求收到 503；`whitelist` 下非 owner Key 全拒
- [ ] 伪造 `X-Forwarded-For` 的直连请求无法伪装 IP（限流按真实来源）
- [ ] Caddy 下 `curl https://域名/v1/models` 走 HTTPS 200（带 Key）

### P9 · 额度感知与告警（**2026-11-05 新增，由真实事故驱动；按多 window 模型重写**）

> **触发事故**：用户 CodeBuddy 额度「1412.73 / 1500、到期 2026-11-05」差点当天过期才被发现。
> 复盘发现**三层缺陷**：
> ① 该渠道根本没接进来（漏接，见 P2）；
> ② **到期信息未参与调度**：`expiryRank()`（`scheduler.go:1796`）对 `ExpiresAt<=0` 返回 `math.MaxInt64`，
> 而活库实测大量 `expires_at=0`、`total=0` → 所有账号到期排序全部相同 = **到期感知失效**，
> `credit_first` 退化为「谁 remaining 大谁先」，正好把「快到期但还剩很多」的账号排到后面；
> ③ **数据结构假设错误**（2026-11-05 复查发现）：aiworkgate 用单组 `remaining/total/expires_at`，
> 而实际额度是**多 window** 模型 —— 一个账号 N 条额度（总积分/基础包/赠送包/免费池），
> 且「到期」有两类完全不同的语义：**`resetsAt`（周期重置）** 与 **`runsOutAt`（券/批次何时烧完）**。
> **用户 CodeBuddy 的事故属后者，旧设计只盯 `expires_at` 根本覆盖不到。**

**做什么**

*额度模型（F-14，必须按此建模）*
1. **多 window 透传**：桥**原样转发**插件产出的 `windows[]`（每项含 `name/amount/limit/used/unit/resetsAt/runsOutAt/runsOut/display`），
   宿主**不做字段强映射**——否则接第 20 个平台必然崩
2. **归一化展示**：面板按 window 分组，直接复用插件的 `display` 字符串（如 `876 / 4600 · 100 即将过期`）
3. **告警三分（Q2=C）**：同一账号三类独立规则，互不覆盖
   - **① 券/批次将失效**（`runsOutAt` 临近）← 用户事故类型
   - **② 周期重置前未用完**（`resetsAt` 临近且 `used/limit` 偏低）← 白扔额度
   - **③ 余额见底**（`used/limit` 超阈值）
4. **阈值每渠道可配（Q3=B）**：全局默认 + 插件级覆盖（有的平台券只活 3 天，7 天阈值无意义）

*用量三栏与成本采集（D-31，2026-11-05 新增）*
9. **`api_logs` 七列一次迁移**：`model_requested / model_upstream / model_served / cache_write / cache_write_1h / cache_unknown / cost_usd / pricing_model`——
   `tap.apply` 补采 `cache_creation_input_tokens` 与响应体 `model` 字段（`tap.finish()` 处用 magpie `fastjson.go:1223 topMember` 方式抓一次），
   `deliver` 回包**不再把客户端要的名字写回去**（现 `envelope.go:768/:793` 的行为）
10. **价格引擎**：`catalog.Price` 式分档价 + 1h 缓存价 + 峰谷价 + 货币换算（`usage.go:515-520 CostAt`、`:745-758 FormatCost` 语义）；
    **供应商级倍率与「模型级已设价格不被覆盖」**（D-30 图三）
11. **KPI 补两格（零成本速赢）**：`SummaryKPI`（`service.go:118-125`）透出已算好的 `LatencyMSSum/TTFBMSSum/TTFBCount` → Overview 补「平均延迟/平均首字」
12. **命中率口径修正**：`prompt_tokens` 含 cached 不扣减 → 分母虚高；修 P0-2 时一并修

**验收**
- [ ] **多 window 渲染**：codearts 账号面板显示「总积分 / 基础积分包 / 赠送积分包」三行，各自的 `display` 正确
- [ ] **券到期告警（事故场景）**：构造 `runsOutAt=今天+3天`、`runsOut=100` → 面板红点 + 通知，文案说明"100 分将于 X 失效"

### P12 · 模型接入配置与「测试模型」（**2026-11-05 新增，D-27**）

> 用户指出：「供应商的各种模型的接入和配置、测试模型、调用策略」。查证 magpie 有完整实现，
> aiworkgate **只有连通性探针（`diagnostics/probes`），没有「对某个模型真发一次请求」的能力**。
> **字段级规格见 [`2026-11-05-供应商配置面板字段规格.md`](./2026-11-05-供应商配置面板字段规格.md)**（用户三张截图的逐项记录，17 项字段与默认值）。

**做什么**
1. **模型测试（搬 `provider/test.go` 1244 行的核心）**：
   - `POST /api/models/{provider}/{model}/test`：发**最小请求**（`max_tokens=1`，一条 user 消息）
   - 返回 `{ok, status, ms, model, error, otherAPI}`（对齐 magpie 的 `Result`）
   - **关键语义**：`otherAPI=true` 表示「厂商说该模型不在这个 API 上」，提示换端点而非判死
   - 批量：`POST /api/models/test` 按供应商并行测，结果落 `probe_results`（复用现 `diagnostics`
2. **供应商预设**（搬 `presets.go`）：`Kind` 分四类 — `vendor`（模型厂）/`relay`（中转聚合）/`local`（本机）/`remote`（另一台 magpie）；新增供应商时只需填 key
3. **模型重命名**（搬 `modelprefs.go`）：模型名可改为用户自定义，**与 vendor 列表分开存**，刷新/重启/升级不丢；对外仍拼 `名字 · 供应商`
4. **推理档位裁剪**：只保留模型部分档位（如六个里留三个），对外列表只给保留的
5. **模型可用性兜底链**（搬 `models.go`）：vendor 列表 → `models.dev` 目录 → 插件自带 → 本地缓存

**验收**
- [ ] 对某真实模型点「测试」→ 真发出最小请求、返回耗时与状态；失败时给出可读原因
- [ ] 厂商说「不在这个 API」时返回 `otherAPI`，提示换端点而不是直接判失败
- [ ] 批量测试并行执行，超时与失败隔离（一个坏不影响其他）
- [ ] 重命名后刷新模型目录，自定义名仍在；vendor 列表变化不影响自定义名
- [ ] 推理档位裁剪后，`/v1/models` 只列出保留档位
- [ ] vendor 拉取失败时自动回落 models.dev / 插件 / 缓存，并在 UI 标注来源

### P11 · 路由分组与规则（**2026-11-05 新增，D-28**）

> 用户截图里的「分组 / 路由组」；查证 magpie 有 8 个专门文件（group/grouprule/groupmatch/groupweight/group_order/group_serve/group_share/grouptemplate）。

**做什么**
1. **分组模型**：一组可含多个成员（模型/其他组），对外作为一个可路由目标
2. **模式匹配入组**（`groupmatch.go`）：`*` 通配、`re:` 正则；**每次读取时按当前模型列表求解**，vendor 新增的模型自动入组
3. **组规则表**（`grouprule.go` 781 行）：按**请求本身可观测的特征**路由——
   长度 / 是否带图 / 思考档位 / 哪个 agent 发来的 / 时段（如厂商高峰价时段）
   **核心约束**：同样请求永远走同样路径（确定性），且 trace 记录「是哪条规则生效」
4. **组权重**（`groupweight.go`）与**组顺序**（`group_order.go`）
5. **意图规则**（唯一例外）：可用判据模型（JEV，见 D-18）判断「难题给强模型、简单给便宜」

**验收**
- [ ] 建一个 `re:` 匹配的组 → 组内成员随 vendor 目录变化自动增减
- [ ] 长请求/带图请求按规则走不同成员；同样请求两次结果一致
- [ ] trace/Explain 能显示「命中了哪条规则」
- [ ] 组权重生效：1:3 的权重下请求分配比例接近
- [ ] 意图规则用 JEV 跑通一例（难题→强模型、简单→便宜）
