## 0 · 前提与边界

- 部署形态（主线 D-07/D-15）：公网服务器只跑 aiworkgate；反代承担 TLS；服务器**不跑** magpie。
- 本机（Windows）可长期关机；服务器 7×24；凭据从本机单向推送到服务器。
- 不采用内网穿透（frp/隧道暴露本机）；服务器由用户自行租用。
- 本文**只写计划，不写代码**（用户 2026-11-05 明确）。

## 1 · 先看资产：攻击者真正想要什么

| 资产 | 价值 | 一旦失守 |
|---|---|---|
| **refresh token（各渠道）** | **最高** | 攻击者可长期冒用你的上游账号额度，且不易被你发现（除非有异常审计） |
| 上游账号本身（codearts/trae/zcode 等） | 高 | 被风控、封号、额度被刷 |
| `agk_` 客户端 Key 与哈希库 | 中高 | 他人白嫖你的额度；若可绕过配额则更糟 |
| 管理面 session cookie | 中 | 改配置、装插件、读请求正文 |
| 请求正文（`api_logs` body） | 中 | 泄露你与他人对话内容/内网信息 |
| 插件市场拉下来的第三方 `.mjs` | **高危入口** | **在服务器上执行任意代码**（见 §4-①） |
| 服务器 shell（SSH） | 最高 | 上面一切归零 |

**结论**：本项目有**两个**最高危面——**SSH 入口**与**第三方插件代码执行**。其余按层收敛。

## 3 · 分层加固（每层给"做什么 / 怎么验"）

### S-1 · 网络入口（今天做）

**做什么**
1. 云安全组/UFW/NFTables 默认 **deny inbound**，只放行 **80/443**。
2. SSH 不做全网开放：优先「固定出口 IP 白名单」；做不到则改高位端口（明确标注：**改端口只降噪，不等于防护**）。
3. 数据库/缓存/管理面板/Docker API **一律不监听公网**；确需远程一律走 SSH 隧道。
4. **aiworkgate 只绑 `127.0.0.1`**（当前 `listen_lan:false` 即符合；服务端配置必须显式写死回环，禁止 0.0.0.0）。
5. Caddy/Nginx 只占 80/443，反代到 `127.0.0.1:7865`。（2026-11-07 核对：实现端口为 7865）

**怎么验**
```bash
ss -tlnp | grep -v 127.0.0.1        # 期望：只剩 80/443 对外
ufw status verbose                   # 期望：deny (incoming) + 仅 80/443/SSH白名单
# 外网侧：nmap -Pn -p- <公网IP>       # 期望：只见 80/443
```

### S-2 · SSH 登录（今天做，性价比最高）

**做什么**（`/etc/ssh/sshd_config`）
```ini
PasswordAuthentication no
PermitRootLogin no
PubkeyAuthentication yes
MaxAuthTries 3
AllowUsers <deploy-user>
```
- 日常用普通用户 + `sudo`；私钥本地加密，定期轮换。
- 叠 **fail2ban**（单机够用）或 **CrowdSec**（要威胁情报/多机协同时选它）。
- 面板类软件（1Panel/宝塔）**若确需安装**：面板端口改高位、开 SSL、限制来源 IP、**绝不暴露公网**。

**怎么验**
```bash
sshd -T | grep -E 'passwordauthentication|permitrootlogin|maxauthtries'
fail2ban-client status sshd
```

### S-3 · 反代与 WAF（本周做）

**做什么**
1. **Caddy 强制 TLS**（自动证书）+ HSTS；HTTP 一律 308 跳 443。
2. WAF 二选一：
   - **雷池 SafeLine**（反代型，Docker）：能识别 sqlmap/Nikto/Nmap 指纹；
   - 或 **Nginx + ModSecurity/CRS**（纯配置，资源更省）。
3. **关键约束（本项目特有）**：`/v1/chat/completions` 与 `/api/logs/stream` 是 **SSE 长连接**。
   反代/WAF **必须关闭响应缓冲**，否则流式会被截断或整段延迟。
   ```nginx
   proxy_buffering off;
   proxy_cache off;
   proxy_read_timeout 600s;
   chunked_transfer_encoding on;
   ```
   **WAF 上线前必须实测流式**：若雷池缓冲导致流式异常 → 把 `/v1/*` 排除 WAF（仅保留 TLS + 限流），或改用 Nginx 直通。
4. **公网不发布 `/api`**：见 §4-②，这是本项目最容易被扫到的口子。

**怎么验**
```bash
curl -sS -o /dev/null -w '%{http_code} %{scheme}\n' https://<域名>/healthz   # 200
curl -sS -N https://<域名>/v1/chat/completions -H "Authorization: Bearer <key>" \
  -H 'Content-Type: application/json' -d '{"model":"...","stream":true,"messages":[...]}' \
  | head -5     # 期望：逐块到达、不整段卡住
```

### S-4 · 应用层（与主线 P5 合并执行）

**做什么**（主线 P5 已含，此处只列安全底线）
1. **无 Key 一律 401**；`keys_scope` 的 fail-open 分支改 **fail-closed**（审计 P1-9）。
2. Key 四道闸：`expires_at`（分享必填）+ `daily_quota` + `max_requests_total` + `model_scope`。
3. 速率限制双维（Key + 真实 IP）；`/v1/*` 默认较严，管理路径若开则更严。
4. **服务开关三态**（主线 D-11）：`paused` 全 503；`whitelist` 只放行 owner Key——这是「我不用时关门」的正式手段。
5. 输入上限：请求体 32MB（既有）之外，SystemOne 按 D-18 ⑧ 在本地判 1MiB/8MiB，**超限即拒**。
6. 错误响应**不回显上游原文中的敏感头**；日志脱敏（Authorization、cookie、api_key 一律 `<redacted>`）。
7. `/health` 与 `/healthz` 只回极简状态（现有行为已符合），勿加版本/内网信息。

**怎么验**
```bash
curl -i https://<域名>/v1/models                                  # 401
curl -i -H "Authorization: Bearer <过期key>" .../v1/models        # 401
curl -i -H "Authorization: Bearer <超配额key>" .../v1/chat/completions  # 429 + 明确文案
# 伪造 XFF：curl -H 'X-Forwarded-For: 1.2.3.4' ...  # 限流仍按真实 IP 生效
```

### S-5 · 凭据保护（与主线 P4 合并执行）

**做什么**
1. 服务器侧凭据库：**文件 0600 + AEAD 加密**（Linux 无 DPAPI；主线已定本地密钥文件）。
2. 密钥与密文**分文件存放**，密钥不进备份包；备份加密。
3. **每渠道隔离**（一条失守不波及全部）+ **一键吊销** + 拒绝 `revoked` 后立即不可用。
4. **`last_used_at` 异常审计**：面板可见；规则化告警（例：某渠道 30 天未主动使用却在凌晨被调用 → 告警）。
5. **凭据同步通道不上公网**：服务器侧同步端点只监听 `127.0.0.1`，本机经 **SSH 隧道**推送（`ssh -L`），并用独立 `sync_token` 二次认证。**这是"内网穿透"的合法替代**（方向是本机→服务器，不暴露本机）。
6. 凭据轮换与吊销流程写进运维手册（谁、何时、怎么验）。

**怎么验**
```bash
stat -c '%a %U:%G %n' <凭据目录>/credentials.enc     # 600
xxd <凭据文件> | head -3                              # 期望：密文而非明文 JSON
ss -tlnp | grep <sync端口>                            # 期望：只绑 127.0.0.1
```

### S-6 · 供应链（**本项目新增的最高危面之一**）

> 主线让 aiworkgate 从 npm/GitHub 装第三方 `.mjs` 并**在服务器上执行**。
> 这等于「把别人的代码请进你的凭据服务器」——必须按"不可信代码"对待。

**做什么**
1. **安装即执行 = 高危**：插件运行在**独立系统用户**下（`aiworkgate-plugin`），
   与凭据库**权限隔离**（插件进程读不到 `credentials.enc`，凭据由宿主注入）。
2. systemd 加固（若以服务运行）：`NoNewPrivileges=true`、`ProtectSystem=strict`、`ProtectHome=true`、
   `PrivateTmp=true`、`RestrictAddressFamilies=AF_INET AF_INET6`、`MemoryDenyWriteExecute`（如与 bun 冲突则记录取舍）。
3. **网络出口白名单**：插件只允许访问其声明的 `network_domains`（现有 manifest 已有该字段），
   超出即拒绝——防止插件被投毒后外传凭据。
4. **版本锁定 + 完整性校验**：安装时记录 tarball SHA256 与版本；更新**默认提示、不自动生效**；
   启用"自动更新"时必须校验签名/哈希并在失败时回退。
5. **更新前人工/自动 diff 摘要**：列出新增网络域名、新增文件、`child_process` 调用点变化。
6. 打包 bun 的**来源固定**：从官方校验过的二进制内置，记录哈希；不接受运行时从网上下载。
7. 禁止 `curl | bash` 安装任何安全脚本（用户提供的仓库也一样：**先下载、读、验签名，再执行**）。

**怎么验**
```bash
systemctl cat aiworkgate 2>/dev/null | grep -E 'NoNewPrivileges|ProtectSystem|PrivateTmp'
ps -o user,pid,cmd -C aiworkgate | head            # 期望：非 root
ls -l <凭据目录>                                    # 期望：插件用户无读权限
# 越权出口测试：插件尝试访问未声明域名 → 期望被拒并有日志
```

### S-7 · 检测与响应（持续）

**做什么**
1. **主机基线**：`rkhunter` + `chkrootkit` 交叉扫描（两个签名库互补），定期跑。
2. **文件完整性**：AIDE 监控 `/etc`、`/usr/local/bin`、aiworkgate 二进制与配置（排除规则必须调优，否则噪音淹没）。
3. **内核审计**：`auditd` 记录关键 exec/文件写入，配合日志外送（邮件/Telegram）。
4. **基线审计**：Lynis 定期跑，看 Hardening Index 是否退化。
5. **应用侧告警**：登录失败突增、`/v1` 401 激增、单 Key 流量异常、凭据 `last_used_at` 异常时段。
6. **补丁策略**：自动安全更新（`unattended-upgrades`），OpenSSH/Nginx/内核/运行时及时升；关注 CVE 公告。
7. **应急**：发现入侵 → 先断网（安全组全拒）→ 保全证据（快照/日志）→ 吊销全部凭据 → 重建而非清理。

**怎么验**
```bash
lynis audit system | tail -20
rkhunter --check --sk | tail -15
aide --check | tail -5
systemctl status auditd fail2ban
```

## 4 · 本项目特有的高危点（逐条必须处理）

### ① 插件市场 = 任意代码执行（**最高危**）
见 §S-6。**没有沙箱的插件市场，等于给攻击者开了一个"合法安装后门"的通道**。
最低要求：独立用户 + 权限隔离 + 出口白名单 + 版本锁定 + 更新需确认。

### ② 管理面 `/api/*` 不应发布到公网
`/api` 是管理面（改配置、装插件、读请求正文）。你手机只用 `/v1`，**没有理由把管理面暴露**。
- 方案：反代只暴露 `/v1/*`、`/healthz`；`/api/*` 返回 404（或仅允许内网/隧道访问）。
- 若确实需要远程管理：走 SSH 隧道或 WireGuard，**不要直接放公网**。
- 这样即使管理面鉴权有未知缺陷，攻击面也是关闭的。

### ③ SSE 与 WAF/反代的兼容性
见 §S-3。流式被缓冲 = 功能事故；WAF 拦截长连接 = 时好时坏。**上线前必须实测**。

### ④ magpie 的 3425 端口绝不可暴露
`F-03` 已实测：magpie 网关**无鉴权**（无 key/错 key 都 200）。服务器不跑 magpie（D-07），
但**本机若将来把 3425 映射出去，等于把 124 个模型白送**。写进红线。

### ⑤ 日志与备份里的明文
- `api_logs` 存请求正文（保留 3 天）→ 正文可能含敏感信息：脱敏 + 短保留 + 不对外。
- `docs/`、`build/`、`*.db.bak-*` 不得随发布包外传；备份**加密**。
- 配置导出功能（若有）必须过滤 `api_key`/`proxy_password`/`token`。

### ⑥ 账号共享的合规风险（非技术，但会现实施加成本）
把上游免费额度分享给他人，**可能违反上游服务条款**，风险是**账号被风控/封禁**，且封禁往往连带你自己的主账号。
建议：分享 Key 只给可信的人；`model_scope` 限定便宜模型；保留"随时全停"的服务开关；**不要用主账号做大规模分享**。

### ⑦ 面板软件本身就是攻击面
1Panel/宝塔历史上都出过严重漏洞。**优先不装面板**；确需安装则：仅内网可达、强口令、面板自身补丁跟上。
你的参考材料里"宝塔闭源、历史事件"的判断是对的——**能用纯 CLI + Caddy 就不引入面板**。

## 7 · 诚实提示

1. 上面每一条都**可验证**（给了命令）；但**没有一条我能替你执行**——服务器是你的，我只能给配置与验收判据。
2. WAF、面板、安全脚本都有**引入新问题的可能**（缓冲破坏流式、脚本自带后门、面板成为新入口）。本文对这三者都给了"不引入/最小引入"的替代。
3. **没有清单能保证不被渗透**。本文目标是：把成本最低的三条路径（SSH 爆破、无鉴权 API、扫描发现管理面）**彻底关掉**，并把"已被入侵能否发现"补上。
4. 你材料里提到的 GitHub 仓库（`fidpa/ubuntu-server-security`、`0x10debug/vps-security-enhancement-scripts`、`lukankan123/vps-skills`）我只作为**参考线索**记录，**未逐个核验其内容与安全性**。使用前按 §S-6-⑦ 的规矩：下载、阅读、验签名，再执行。
