- **已有地基**：`gateway.AnalyzePrompt`（internal/gateway/prompt_compose.go:31-91）已实现六段 char-weighted 拆解（system/tools/memory/history/user_input/other，D-55），三 envelope 通吃，但**只在按需分析接口**（internal/app/prompt_analyze.go:16-17，Scheduler 粘贴分析）调用，不在请求热路径。
- **六维口径与 D-55 六段的差异**：六维要新增「工具结果」独立桶（现归 history）、新增「文件」（现不可判）、「记忆」要扩到启发式（现只认顶层 memory/memories 字段，几乎无人传）。
- **建议架构**：采样门控（仿 trace.go sticky 模式）+ 独立表落盘 + 纯 CSS treemap。TraceEvent 契约冻结勿动。

| 记忆 | 顶层 memory/memories（:51-56，现实很少传） | 同 | 同 | **仅启发式**（需标记约定） |

启发式草案（二期）：
- 文件：文本块内路径正则（POSIX `/[\w.-]+(/[\w.-]+){2,}`、盘符 `[A-Za-z]:\\...`）、markdown 围栏块头部、`<file path="…">` 类约定标签。误判风险：编码类对话中路径串密度高，会把会话内容误归「文件」；建议只在条级展示页标注命中区间，不进聚合柱。
- 记忆：`<memory>`/`[记忆]`/CLAUDE.md/AGENTS.md 内容块约定。风险：无约定的客户端完全漏归（归回会话内容，无伤大雅）；约定客户端可精确。
- 两者均建议**默认关、采样页可见**，不影响六类主图精度承诺。

## 3 · token 对账口径

- 本地估算（char-weighted）与上游 usage.prompt_tokens（tap.go 采集）存在系统性偏差（工具 schema 的 JSON 序列化口径、消息包装 overhead、cache 前缀）。
- 方案：**比例分摊**——`usage.prompt_tokens × (section_est / total_est)` 逐桶重分摊；展示层同时给「上游总 tokens」与「估算拆分」两个口径，treemap 用分摊值。不引本地 tokenizer（与 D-55 决策一致）。
- 边界：usage 缺失（usage_known=false）时只展示估算口径并标注。

## 4 · 性能评估

- 554K body 的 AnalyzePrompt = 全量 `json.Unmarshal` deep parse + 递归遍历 + `estimateJSONTokens` 对 other/tools 子树的 re-Marshal。参照脱敏 bench（1MiB 全解析改写 <5ms，redact_bench_test.go:36-49），AnalyzePrompt 估 **2-5ms/554K**，无改写但 Marshal 子树是额外项。
- 结论：**不可每请求无条件算**。方案（按优先级）：
  1. **sticky 门控**（照抄 trace.go:5-7 模式）：有订阅者（前端开着 Treemap 页）才开启采集，未开启付一次 atomic 读；
  2. 与 MaskJSONBody/tool-alias 同位单遍（tool_alias_writer.go:40 已验证），避免二次解析 body；
  3. 只算通过门控的请求（或仅 >N KB 的大请求可选），结果挂 reqRecord 收束时落独立表。
- 不复用 redact 的解析结果：redact 开启时 MaskJSON 返回的是改写后字节，六维应**在改写前**的 body 上算（语义=用户真实上下文），或明确取改写后口径（对账更接近上游所见）——实现卡需二选一并记录。

## 5 · 前端方案（不引依赖）

- squarified treemap 是几十行纯 JS 行打包算法 + CSS absolute 矩形定位，与项目惯例一致（Usage 热力图即手写，无图表库）。
- 数据结构草案：
  ```json
  {
    "req_id": "…", "total_tokens": 123456, "upstream_prompt_tokens": 130000,
    "sections": [
      {"key": "tools", "tokens": 42000, "items": [
        {"label": "tool:read_file(2.1k)", "tokens": 2100, "kind": "tool"}
      ], "other_count": 37, "other_tokens": 18000}
    ]
  }
  ```
- 类内 Top-8 + 「另外 N 项」聚合块；条级 item 仅在采样返回里带（label=角色+序号+首 40 字），hover title 给完整前缀。
- 归属页建议：Usage 或 Trace 时间线点开单请求 → 详情抽屉渲染 treemap（req_id 从独立表取数）。

## 6 · 落点建议

- **TraceEvent 不动**（internal/gateway/trace.go:12-29 契约冻结，task-49 前端照此消费）。
- **独立表 `ctx_compositions`**（建议）：`req_id, ts, total_est, sections_json, items_json, sampled_reason`。理由：api_logs 已 20+ 列且逐轮迁移（store.go:162-723 v1→v28），六维行大（条级 items）、写入频率低（门控采样）、查询模式独立（按 req_id 单条取）；独立表 + 既有保留期清理机制即可。若 Lead 倾向 api_logs，则加单个 `ctx_composition TEXT` JSON 列（语义同 task-60 cached_tokens 先例），代价是宽表继续变宽。
- 收束点：trace 的 emit 收束点（trace.go:224 `traceEventOf` 所在的请求唯一出口）旁落库，与 tap usage 对账同刻。

## 7 · 分期建议

- **一期（全部精确）**：AnalyzePrompt 升级六维口径（+tool_results 独立桶、user/assistant 条级清单）；sticky 门控采样；独立表落库；前端六类 treemap（不含类内 item 钻取）+ 上游对账分摊。
- **二期（启发式）**：文件/记忆启发式识别（默认关）；类内 Top-N 展开 + 条级钻取；「估算 vs 上游」双口径视图。
