## 1 · 为什么「装插件」要按供应链对待

插件市场 = 把别人的代码请进**凭据服务器**并在服务器上执行。三个具体风险：

| 风险 | 具体形态 | 本卡的对应措施 |
|---|---|---|
| 投毒（同名版本替换） | 上游把 `1.4.2` 的内容换掉，指纹不变、版本号不变 | 同版本不同哈希 **直接拒绝**（§2.3） |
| 升级即扩权 | 新版多声明域名、多出文件、多起子进程 | 更新差异摘要 + `--fail-on-new-domains` 闸门（§4.2） |
| 运行期拉后门 | 安装脚本 `curl bun.sh/install \| bash`，或启动时下载 | bun 哈希锁定 + `audit` 动词（§5） |

**没有锁定与差异审查的自动更新**，等于把这些风险的判定权全部交给上游。

## 2 · 锁定文件：格式与语义

### 2.1 `p8-artifact-lock.tsv`（插件 tarball / 二进制）

```
# p8-artifact-lock v1
# id	kind	version	sha256	bytes	recorded_at	source
opencode-trae-auth	tarball	1.4.2	9f2c…（64 hex）	183424	2026-11-05T15:00:00Z	@magpie-community/opencode-trae-auth
bun	bun	1.4.4	ad86…	115343360	2026-11-05T15:00:00Z	bun-linux-x64.zip
```

- 一行一 artifact，**后写覆盖**该 id 的当前行；被替换的旧行追加到 `p8-artifact-lock.tsv.history`（可追溯"什么时候换过什么"）。
- `recorded_at` 用 UTC（`date -u +%Y-%m-%dT%H:%M:%SZ`），跨时区可比较。
- 锁文件本身要进版本库（它是"我们批准过什么"的证据），`.history` 一并进。

### 2.2 三个动词

| 动词 | 是否写盘 | 用途 |
|---|---|---|
| `record` | 默认 dry-run，需 `--apply` | 安装时记录；升级时更新 |
| `verify` | 只读 | 安装/启动前校验；不符即拒绝 |
| `list` | 只读 | 人工核对现状 |

```bash
# 安装时：先校验再解压
scripts/p8/p8-artifact-lock.sh verify --id opencode-trae-auth --file /tmp/trae-1.4.2.tgz --version 1.4.2
# 首次纳管：记账
scripts/p8/p8-artifact-lock.sh record --id opencode-trae-auth --kind tarball \
    --file /tmp/trae-1.4.2.tgz --version 1.4.2 --apply
```

### 2.3 三种非对称情况的处置（这是锁定的全部价值）

| 情况 | 动作用 | 理由 |
|---|---|---|
| 同版本 **同**哈希 | 幂等，不写盘 | 重复执行安全 |
| 同版本 **不同**哈希 | **拒绝（exit 2）**，不提供"强制覆盖" | 同版本内容变化＝上游换了包 → 必须人工核对，不许一键覆盖 |
| 新版本 | 允许 record，旧行进 history | 正常升级，留痕 |
| `verify --version` 比锁记录**旧** | **拒绝（exit 2）**，除非 `--allow-downgrade` | 降级常被用来复活已修的漏洞版本 |

本机实测（fixture，非真实包）：

```
# 篡改后校验
校验 id=trae  锁版本=1.4.2  锁kind=tarball
  期望 sha256：9f2c…
  实际 sha256：e85d…
拒绝：哈希不符：… 与锁记录不一致（版本锁定生效，拒绝安装）。
  若这是刻意的版本升级：先 record --version <新版本> --apply 更新锁记录并留痕。
  若你没打算升级：**这个 tarball 不可信，不要装。**
（exit=2）
```

## 3 · 安装/启动流水线要接哪几步（给 P2 安装器的接线说明）

```
下载 tarball
  → ①【校验】p8-artifact-lock.sh verify --id <id> --file <tgz> --version <v>
       不符 → 中止，保留 tarball 供取证，日志写 reason=HASH_MISMATCH
  → ②【解压到临时目录】绝不解压到 plugins/ 覆盖现有版本
  → ③【差异摘要】p8-diff-plugin-versions.sh --old <现有>/ --new <临时>/
       输出进安装档案（D-58 的人工审查记录就是这份）
  → ④【闸门】若策略=自动更新：--fail-on-new-domains 有新增域名 → 退回"提示"
  → ⑤【原子替换】目录 rename（先 backup 旧版 → 失败可回退，见 §4.3）
  → ⑥【记账】p8-artifact-lock.sh record … --apply
```

**②③④ 不能省**：直接覆盖目录的话，一旦新版有问题，回退点和证据都没了。

## 4 · 更新策略：「提示优先」

### 4.1 默认行为（契约要求）

**默认「提示」不「自动」**：发现新版本 → 面板红点 + 事件记录，**不下载、不安装、不生效**。
用户点确认后才走 §3 的流水线。

理由：服务器插件带着凭据往前跑，一次静默升级的回滚成本远高于人类点一下的成本（D-58 已定"装前人工审查"）。

### 4.2 启用自动更新的**全部前置条件**（缺一不许开）

| # | 条件 | 不满足时的行为 |
|---|---|---|
| A-1 | `p8-artifact-lock.sh verify` 通过（哈希+pinned 版本） | 中止，转"提示" |
| A-2 | `p8-diff-plugin-versions.sh --fail-on-new-domains` 无新增域名 | 中止，转"提示"（新增域名必须人看） |
| A-3 | 差异摘要里 `child_process` 无新增 | 转"提示"（能起子进程就能绕出口白名单） |
| A-4 | 新版 `egress.strict` 仍为 `true`（不得被上游偷偷关掉） | 拒绝升级 |
| A-5 | 旧版备份已生成且可回退 | 中止 |
| A-6 | 磁盘剩余空间 ≥ 3× tarball 体积 | 中止（避免解压把盘写满导致服务全挂） |

**A-1~A-6 全满足才允许自动装**；任何一条不满足都降级为"提示"，而不是"算了照装"。这条要写进代码，不能只在文档里。

### 4.3 失败回退（验收第 4 条）

```
plugins/<id>            ← 当前
plugins/<id>.bak-<ts>   ← 上一版（升级前 rename，不是 copy，省空间也省时间）
```

- 升级流程：`mv <id> <id>.bak-<ts>` → `mv <临时> <id>` → 启动健康检查（端口探测 + `/health`）
- 健康检查失败 → `mv <id> <id>.failed-<ts>` → `mv <id>.bak-<ts> <id>` → 重启 → 记事件（含失败原因、两个版本号、哈希）
- **保留策略**：每个插件只留最近 2 个 `.bak-*`，更旧的删除（否则服务器被备份撑满 → 另一种可用性事故）
- 失败后**不得**自动重试同一个新版（避免反复把服务打挂）；标记该版本"需人工处理"

### 4.4 检查节奏

对齐 magpie 的 6h 节奏（F-05：`plugin-updates.json` 记 `checked/updated`）。**检查**（只发 HTTP 请求比对版本号）可以自动；**安装**按 §4.1/§4.2。

## 5 · bun 二进制：来源固定，禁止运行时下载（P8-⑥⑦）

### 5.1 规则

1. bun **随包内置**（D-05），不从网上按需取。
2. 哈希写进 `p8-bun-pin.tsv`，启动前校验。
3. 二进制权限必须 `组/其他不可写`（否则可被原地替换，校验就成了摆设）。
4. 安装脚本/桥代码里**不得出现**下载 bun 的 URL，也不得出现 `curl | bash` 形态的安装。

### 5.2 pin 文件格式与用法

```
# p8-bun-pin v1
# version	sha256	bytes	filename	recorded_at
1.4.4	ad864bc6…	115343360	bun-linux-x64.zip	2026-11-05T15:00:00Z
```

```bash
# 纳管（首次打包时，在构建机上）
scripts/p8/p8-bun-hash.sh record --file /opt/aiworkgate/bin/bun --version 1.4.4 --apply
# 每次启动前（或 systemd ExecStartPre）
scripts/p8/p8-bun-hash.sh verify --file /opt/aiworkgate/bin/bun --version 1.4.4
# 供应链审计（发布前；命中即 exit 2）
scripts/p8/p8-bun-hash.sh audit --path ./scripts --path /opt/aiworkgate
```

`verify` 会做三件事：哈希比对、`bun --version` 自报版本交叉核对（防止"换了个二进制但 pin 没动"）、权限判据。

### 5.3 `audit` 的三条规则（把「禁止 `curl | bash`」变成可执行）

| 规则 | 命中示例 |
|---|---|
| `bun.sh/install`、`bun.sh/download` | 运行时下载 bun |
| `npm i -g bun` / `npm install --global bun` | 绕过哈希纳管 |
| `curl|wget … \| sh|bash`（含 `sudo` 变体、`sh <(curl …)` 变体） | 任何管道装脚本 |

本机实测：造一个含 `curl -fsSL https://bun.sh/install | bash` 的安装脚本 → `audit` 命中并 `exit 2`；干净目录 → `exit 0`。

> 契约 §P8-⑦ 也要求**用户提供的第三方安全仓库**（`fidpa/ubuntu-server-security` 等）按此规矩处理：**先下载、读、验签名，再执行**。`audit` 是这条纪律的自动检查部分；"读"和"验签名"仍是人工动作，不能自动化。

## 6 · 更新差异摘要：怎么读（P8-⑤）

`scripts/p8/p8-diff-plugin-versions.sh --old <dir> --new <dir>` 输出五段。本机 fixture 实测原文（节选）：

```
[2] 网络域名（manifest.permissions.network_domains）
  旧版 2 个 / 新版 3 个
  ★ 新增域名 1 个（插件被投毒后外传数据的常见载体，逐个确认真实必要）：
    + telemetry.evil-collect.example

[3] 文件
  改 3 / 新 1 / 删 0
    + lib/extra.mjs
    ~ index.mjs

[4] child_process 调用点变化
  引用（import/require）行数： 旧 1 -> 新 2
  ★ 新增 2 处 child_process 引用（能起子进程 = 能绕过出口白名单的典型手法）：
    + index.mjs	import { spawn, execSync } from "node:child_process";
    + lib/extra.mjs	import cp from "node:child_process"; cp.exec("id");
```

**人工审查口径（D-58 的"看一眼"具体是看什么）**：

| 段 | 看什么 | 判定 |
|---|---|---|
| 版本 | 版本号是否变了 | 变了才算正常升级；没变但内容变了 → 红灯 |
| 域名 | 每个新增域名是否与插件声称的功能匹配 | 出现 `telemetry/collect/analytics/cdn/track` 之类 → 重点看 |
| 文件 | 新增的 `.mjs`/`.js` 是否在被 import 链上 | 只被 `test/` 引用的可低风险 |
| child_process | 新增是否必要（有的插件要起 CLI） | 无法解释的子进程调用 → 拒绝 |

**已知限制**（写清避免误信）：域名提取是 JSON 文本扫描（manifest 若被注释/写成表达式则提取为空）；`child_process` 检测是 grep 级，动态拼接（`process["chil"+"d_process"]`）与混淆检测不到 —— 这类必须人工读代码。
