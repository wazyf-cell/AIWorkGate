## 4 · 关键取舍（每条都是书面决定，不是默认值）

### 4.1 `MemoryDenyWriteExecute` 与 bun 的 JIT —— 不可兼得（**P8-② 点名要求记录**）

**结论：取 `MemoryDenyWriteExecute=no`，并用补偿控制抵消缺失项。**

推理链：

1. `MemoryDenyWriteExecute=yes` 让内核拒绝一切「先写后执行」的内存映射（W^X）。
2. bun 内置 **JavaScriptCore**；JSC 的 JIT 必须把生成的机器码写进可执行页。开启即崩（SIGSEGV 或启动失败），不是性能退化，是**不可用**。
3. 契约 D-05 已定「打包 bun」，所以不存在「换运行时」的选项被顺手采纳；`node --jitless` 是 Node 专有能力，bun 无等价开关（`bun build --compile` 也不改变这点）。
4. **若将来必须开 MDE**：唯一路径是放弃 JIT（换运行时 / 预编译），那属于**架构变更**，必须回写决策台账 D-05，不允许在 unit 里改一行交差。

补偿控制（`aiworkgate-plugin@.service` 里已开）：

| 控制 | 抵消什么 |
|---|---|
| `NoNewPrivileges=yes` + `CapabilityBoundingSet=`（空） | 提权（setuid/文件能力） |
| `ProtectSystem=strict` + `ReadWritePaths`（仅两处） | 改盘、改自身代码、写启动项 |
| `ProtectHome=yes` | 读用户 home 下的 `plugin-auth.json` |
| `PrivateTmp=yes` / `PrivateDevices=yes` | 借 `/tmp` 或设备节点与宿主交换数据 |
| `RestrictAddressFamilies=AF_INET AF_INET6` | 用 AF_PACKET/原始套接字绕出口白名单 |
| `SystemCallFilter=@system-service` + `SystemCallArchitectures=native` | 危险 syscall、32 位 ABI 绕过 |
| `RestrictNamespaces` / `LockPersonality` / `ProtectKernel*` | user namespace 逃逸链、内核面改动 |

**风险边界（写清以免被当成"已经安全"）**：W^X 缺失意味着「恶意代码可以在进程内就地生成并执行 shellcode」这一步无法阻止；上述补偿控制限制的是**生成之后能做什么**。如果攻击者已能在插件进程内执行任意代码，那么凭据隔离（读不到 `credentials.enc`）才是最后一道墙 —— 这也是 4.4 必须解决的原因。

### 4.2 `RestrictAddressFamilies=AF_INET AF_INET6` 移除了 `AF_UNIX` —— 已知副作用

契约原文只写 `AF_INET AF_INET6`，本卡按原文执行，但把副作用写下来：

| 受影响面 | 机制 | 我们的处置 |
|---|---|---|
| journald 直写日志 | `/run/systemd/journal/socket` 是 `AF_UNIX` | 单元用 `StandardOutput=journal`，由 systemd 捕管道，**不受影响** |
| nss-systemd 用户名解析 | varlink 走 `AF_UNIX` | 保证 `aiworkgate-plugin` 存在于 `/etc/passwd`（脚本会写），且 `/etc/nsswitch.conf` 的 `passwd:` 保留 `files` 在前 |
| systemd-resolved DNS | `127.0.0.53` 走 UDP/TCP = `AF_INET` | **不受影响** |
| 任何自建 unix socket 的插件 | 直接失败 | 已知限制；若某插件确实需要，改成 `RestrictAddressFamilies=AF_UNIX AF_INET AF_INET6` 并在安装档案里记一条例外（不允许静默放宽） |

### 4.3 `ProtectHome=yes` 是**故意**的，不是加固副产品

magpie 的凭据在 `~/.config/magpie/plugin-auth.json`。服务器上插件桥**不需要也不允许**看到它 —— 凭据由宿主注入（D-08：refresh token 在服务器，宿主解密后注入）。
因此 `ProtectHome=yes` 同时承担两件事：① 通用加固；② **把"凭据文件在磁盘上"这件事从插件的视野里彻底删掉**。本机（登录机）形态另论：那里插件读本地 magpie 配置是设计的一部分，不套这层 unit。

### 4.4 独立用户的**真实缺口**：只装 systemd 单元，`ps -o user -C` 永远通不过

这是本卡最重要的实现发现，必须写进 P1-1/P8 实现卡：

```
internal/plugins/supervisor.go:166   cmd := exec.Command(exe, mf.Entry.Args...)
internal/plugins/supervisor.go:178   cmd.SysProcAttr = pluginProcAttr()
internal/plugins/sysproc_other.go:13 func hideWindow() *syscall.SysProcAttr { return nil }
internal/plugins/sysproc_other.go:16 func pluginProcAttr() *syscall.SysProcAttr { return hideWindow() }
```

Linux 上 `pluginProcAttr()` 返回 **nil** —— `syscall.SysProcAttr` 里既没有 `Credential{Uid,Gid}`，也没有任何换用户逻辑。**子进程直接继承宿主 uid。**

推论：宿主怎么加固都没用，**插件进程 = 宿主进程的 uid**。所以 P8-① 的验收项 `ps -o user -C aiworkgate-plugin` 要成立，必须在 **spawn 路径**上换 uid。四条可选实现（`p8-create-plugin-user.sh` 也会打印同样的 A/B/C 清单，D 见下表末行）：

| 方案 | 做法 | 代价 / 前提 |
|---|---|---|
| **A. systemd-run 透明单元**（推荐） | 宿主对每个插件执行 `systemd-run --quiet --collect --scope --uid=aiworkgate-plugin --gid=aiworkgate-plugin --property=NoNewPrivileges=yes -- /opt/aiworkgate/bin/magpie-bridge …` | 宿主需要能调 `systemd-run`（root 或 polkit 授权）；端口探测/健康检查语义不变 |
| **B. sudoers 定向授权** | `/etc/sudoers.d/aiworkgate-plugin`：`aiworkgate ALL=(aiworkgate-plugin) NOPASSWD: /opt/aiworkgate/bin/magpie-bridge`，再 `sudo -u aiworkgate-plugin -- …` | 新增 sudo 面；必须**单命令白名单**，不许通配 |
| **C. 静态单元模板** | `aiworkgate-plugin@<id>.service` 由 systemd 托管插件桥，宿主只编排不 spawn | 宿主失去 direct spawn 的时序控制，需改为 socket/端口探测 |
| **D. 原生 `SysProcAttr.Credential`**（**已实现**，task-13） | `sysproc_other.go` 的 `pluginProcAttr(user)` 解析用户名 → `SysProcAttr{Credential:&syscall.Credential{Uid,Gid,NoSetGroups:false}}`；**opt-in**（`plugins.Options.PluginUser` 为空=关闭）；非 root 或用户不存在 → 回落宿主 uid + supervisor 打 warn，不 crash | 宿主须以 root 运行（或持 `CAP_SETUID`/`CAP_SETGID`）；**不提供** `RestrictAddressFamilies`/`SystemCallFilter` 这类 unit 级加固 |

四条的共同点：**子进程 uid 必须是 `aiworkgate-plugin`**。D 与 A/B/C 的取舍：D **完全不影响 spawn 时序**（端口探测/健康检查语义零改动），也不需要 polkit 授权或 sudoers 面（A 的好处是宿主可保持非 root，B 的代价是多一个 sudo 面）；但 D 只管"换 uid"，拿不到 unit 级加固，所以推荐**D 负责换 uid、C（或 A）负责 unit 加固，两者叠加**，而不是二选一。当前状态：D 的代码已落地（`internal/plugins/sysproc_other.go`，Windows 侧行为零变化），**Linux 运行时与 P8-① 验收仍需服务器实跑**（见 §7 验收 1）。

### 4.5 出口白名单的两层，以及为什么必须两层

一句话：**L7 只能看见走了代理的流量；L3 才能保证流量必须走代理。**

- **L7（宿主侧 CONNECT 监听器）**：`internal/egress` 已经为每个 (plugin, account) 绑一个 loopback CONNECT 监听器，`forwarder.go:320-333` 解析 `host:port`，`forwarder.go:344-353` 已经在写 `ProxyResultDenied` 行。域名白名单的判定点就在**解析出 host 之后、`dialUpstream` 之前**（详见 01 号文档 §5）。
- **L3（内核侧）**：插件用户 `skuid` 只允许访问回环（到宿主的监听器），其余 `drop`。这样「绕过代理直连」不是"没被发现"，而是**连不通**。

为什么需要 L3：magpie 插件只 import `node:*`（F-01），而 **Node 的 `https`/`net` 不会自动读取 `HTTP_PROXY`** —— 代理是靠桥在进程内做拦截（`globalThis.fetch`/`https.request` 改写）才走得通的。如果插件用原始 socket 直连，L7 根本看不到它。L3 让这种绕过变成"插件自己坏了"，而不是"数据静默外泄"。

**这个取舍的代价要认**：L3 硬阻断 + 不读代理的插件 = 插件直接不可用（fail-closed）。所以落地顺序必须是「先在桥里做拦截 → 用 L3 关掉旁路 → 观察线上无回归」，不能反过来。

### 4.6 `SystemCallFilter=@system-service` 的已知摩擦

bun/JSC 可能用到 `memfd_create`、`mprotect`（JIT 必需，`@system-service` 含 `mprotect`）、`futex`、`epoll_*` —— 这些都覆盖。若实测被错杀（表现为 `EPERM` 或启动即崩），处置顺序：
1. `SYSTEMD_LOG_LEVEL=debug systemd-run --property=SystemCallFilter=@system-service …` 抓被拒 syscall；
2. 用 `SystemCallFilter=~@system-service @system-service:memfd_create` 形式**逐条加白**，不要整条删掉；
3. 每次例外都要写进安装档案（同 D-58 的人工审查记录）。

| `ProtectSystem` | `strict` | 全盘只读，仅 `ReadWritePaths` 可写 | 契约点名项；必须配 `ReadWritePaths` |

| `RestrictAddressFamilies` | `AF_INET AF_INET6` | 只留 IP 套接字 | 契约点名项；`AF_UNIX` 副作用见 4.2 |
| `MemoryDenyWriteExecute` | `no` | —— | **4.1 的书面取舍**；`=yes` 与 bun 不可兼得 |
| `PrivateDevices` | `yes` | 无设备节点 | 推荐项 |
| `ProtectKernel{Tunables,Modules,Logs}` / `ProtectControlGroups` / `ProtectClock` / `ProtectHostname` | `yes` | 内核面只读 | 防时间伪造绕过证书/JWT |

| `SystemCallFilter` + `SystemCallArchitectures` | `@system-service` + `native` | syscall 白名单 | 摩擦见 4.6 |

## 6 · 完整性 / 更新 / bun 来源（摘要，细节见 02 号）

- **锁定**：`p8-artifact-lock.tsv` 一行一 artifact：`id → kind, version, sha256, bytes, recorded_at, source`；旧值进 `.history` 可追溯。
- **拒绝语义**：哈希不符 → `exit 2` + 「拒绝安装」；**同版本不同哈希 → 直接拒绝**（同版本内容变化＝供应链红灯，不提供一键覆盖）。
- **降级**：`verify --version` 比锁记录旧 → 拒绝，除非显式 `--allow-downgrade`。
- **更新策略「提示优先」**：默认**不自动装**；自动更新必须同时满足 ① 哈希校验通过 ② `--fail-on-new-domains` 闸门无新增域名 ③ 失败可回退上一版目录（备份保留）。
- **bun 来源固定**：`p8-bun-pin.tsv` 钉 `version → sha256`；`audit` 动词扫描安装脚本/桥，出现 `bun.sh/install`、`npm i -g bun`、`curl|wget … | sh` 即 `exit 2`。

## 9 · 诚实声明（哪些没验、为什么不验）

1. **所有 Linux 系统行为未实跑**：`useradd`、`install -d -o/-g/-m`、`chown` 语义、`runuser` 切换、`systemd-analyze verify`、`systemctl cat`、真实 `chmod` 位。本机 Windows 11 + Git bash（MSYS）没有这些工具；**MSYS 连组/其他写位都不映射**（实测 `chmod 757` 后 `stat -c %A` 仍为 `-rwxr-xr-x`），所以连「权限判据」都改用 `--perm-override` 注入符号串来验证逻辑，而不是伪造成"已在 Linux 验证"。
2. **出口白名单未实现**：本卡只出规则、语义、记账口径与 21 条测试矩阵。P8 验收第 2 条在实现前**不可能通过**，不要拿本文当"已完成"。
3. **`RestrictAddressFamilies` 的 AF_UNIX 副作用未实测**：结论来自 systemd/nss 的工作机制（journald socket 是 AF_UNIX、nss-systemd 走 varlink），没有在服务器上跑过 `ls /run/systemd/journal/socket` 的失败复现。
4. **`SystemCallFilter=@system-service` 对 bun 的摩擦未实测**：可能缺 `memfd_create` 等；4.6 给了排查与逐条加白的方法，但没有实测清单。
5. **本卡未安装、未启动、未修改任何系统服务**，也未触碰 `internal/**`、`opchost/**`、`webui/**`、`plans/**`。
6. **`bun build --compile` 是否真能产出可用 exe** 沿用第三轮 handoff 的结论（`docs/handoff-20261105-aigate-third-round.md` §9.2：**未实测**），本文不重复声称为已验。
