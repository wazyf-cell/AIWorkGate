## 三个设计决定及理由

1. **fixture 是手写合成数据，不是录制真实响应。** 录制会把真实账号 id、真实 client key 前缀写进仓库，违反交接 §6「Key 明文与密码不落盘」；而且录制内容每天变，门禁会因数据漂移而非样式回归变红。字段名与嵌套是照着真实响应一次性读出来的，所以视图走的是正常渲染分支。行数固定（日志 12 行、账号 5 行、资源 3 行），因为行数影响表格高度。
2. **基线绑定浏览器引擎。** 实测同一 bundle 在 Chrome 与 Edge 下差 0.12–0.46% 像素（整片文字区的字形栅格差异），不是布局改动。为此放宽容差会连真实回归一起吞掉，所以 `visual-baseline/.engine.json` 记录产出引擎，换引擎直接报错并给出两条出路，而不是给出无意义的像素差。
3. **截全页，不是只截视口。** 曾经只截 900px 视口，实测 `.card` 底部在 y=1061，**折叠线以下的样式回归完全不会被发现**（同一注入在修复前为绿、修复后为红，已实测）。

### 3. 商汤二维码"秒过期"：定位到根因，但不是插件 bug

用真实 code 直连上游取证：

| 探测 | 结果 |
|---|---|
| `POST /api/web/auth/v1/login_with_qrcode_code`（插件生成的 code） | `{"code":0,"data":{"status":"pending"}}` —— **无 `expired_at` 字段** |
| 同一 code 连问 3 次 | 3 次都 `pending`，不转 canceled |
| 随机伪造 code | 同样 `pending`（上游不校验 code） |
| 插件生成的二维码内容 `https://xiaohuanxiong.com/login/mp?code=...` | **HTTP 404** |

**结论**：这个登录流程在当前上游状态下**不可能成功**——二维码指向的深链是 404，而轮询端点对任何 code 都只回 pending。用户看到的"过期"最可能来自：(a) 扫码后 App 打开那个 404 深链自己报的错，或 (b) 用户手动关掉弹窗后 `/qr/{sid}` 页因会话被 DELETE 而显示"登录会话不存在或已过期"。

`login.go:14-17` 的注释早已实测记录过这一点（"the payload URL answers HTTP 404 in a desktop browser... the poll endpoint answers pending for any code"）。**这是上游侧限制，不是本插件的编码错误**，我不打算用改代码的方式去"修"它。
