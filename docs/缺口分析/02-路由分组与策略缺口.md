## 0. 一句话结论

magpie 把「路由」做成了**三层可组合的策略栈**（模式 → 组规则 → 亲和/冷却），11 种路由模式 + 12 种组规则条件 + 8 种冷却原因分级 + 15 种粘性 `why`；aiworkgate 把「路由」做成了**一层选择函数**（6 种账户内策略 + 2 种池间模式 + 2 种 TTL 粘性 + 3 种冷却结果）。aiworkgate 在**确定性选择质量**（`p2c`）、**并发治理**（账户级并发上限）、**首字节对冲**（hedge）、**熔断**上反而更强。

**关键修正**：任务简报说「9 种路由模式」，实测 magpie 是 **11 种**（9 种基础 + `cheap` + `expiring`），且真正的策略实现不在 `internal/provider/routing.go`，而在 `internal/routes/`（`routes.go` 202 行 + `strategies.go` 597 行 + `fastest.go` 148 行 + `round.go` 102 行）。`internal/provider/routing.go` 只放常量与「怎么改路由」的函数。

## A.2 冷却分级（`routing.go` 前 20 行注释 + 实现）

**文件头注释** `gateway/routing.go:3-14`（原文）：

```go
// Routing spreads a provider's requests over the keys or accounts it has
// on (see provider.Provider.Routing): smartly, in order, in turn, or the
// least used first. Whichever goes first, a key that suits the request
// still goes before one that doesn't, and one resting after a failure
// waits at the back for as long as its failure says: out of credit for
// half an hour, out of quota until it says it resets — or, for a
// subscription, until the window it filled does — rate limited until it
// says to try again, and otherwise a minute, longer each time it fails
// again. A rest's length and what set it go into the trace as they are, so
// what the Routing page says is when the account really comes back.
```

## A.3 备用链（fallback）三条语义

### A.3.1 语义一：仅在「回复开始前」切换

**文件头注释** `gateway/fallback.go:3-9`（原文）：

```go
// Fallback: a provider can name models to use when it can't take a request
// — a coding plan out of quota, a rate limit, an overloaded or failing
// vendor. The request goes to the next one only while none of the reply has
// been sent, so an agent sees one clean answer from whoever gave it, never a
// half from each. A provider that just failed that way waits at the back of
// the line for a minute, rather than costing every request a doomed try.
```

**实现链**（不是单一 `bool`，而是三级判定）：
1. **缓冲区门**：`gateway/fallback.go:2955-2970` `holdWriter` / `alive` 结构，`sent` 记「这条流的 200 和响应头是否已经发出」，`told` 记「最后一次给 agent 发东西的时间」。
2. **事件级通过**：`gateway/refusal_handover.go:60-63` `overActive()` = `h.over != nil && !h.over.spoke && h.passing && h.stream && !h.handedOver` —— **reasoning / 只作框架的帧已经流出去，但正文一个字都没说，仍可整体移交给下一个候选**（`gateway/refusal_handover.go:15-19` 注释 #248）。
3. **交接**：`gateway/refusal_handover.go:69` `passOver(b)`；失败后写回 `errHandedOver`（`gateway/refusal_handover.go:41`），`gateway/fallback.go:2560-2566`：
```go
if h.overActive() {
    // nothing said yet: a refusal is handed to the next candidate
    h.passOver(b)
    if h.handedOver {
        return 0, errHandedOver
    }
    return len(b), nil
}
```
4. **已开始后不允许重连**：`gateway/fallback.go:1892` `lateRests`（回复中途断了怎么算）；`gateway/fallback.go:2628-2637` `mayReloop`：Anthropic/Responses 的流一旦 `message_start`/`response.created` 发出，**不能**用另一个流接上（只有 Chat 协议的增量可以），否则结束并报错。
5. **哪些错误才换**：`gateway/fallback.go:1854` `retryable(status, body)` —— 401/402/403/404/408/429/>=500 可换；`overflow`（对谁都太长）不换；`modelRetired`/`EdgeBlocked`/`failCredit`/`quotaWords`/`shapeWords` 等按正文判断。

### A.3.2 语义二：失败者排队尾 1 分钟

- **常量**：`gateway/fallback.go:43` `const fallbackCooldown = time.Minute`（注释即 `fallback.go:8-9`「waits at the back of the line for a minute」）
- **排队实现**：`gateway/fallback.go:1240` `restLast(out, pl)` —— 把候选分四类 `ready` / `busy` / `resting` / `last`，顺序为 `ready ++ busy ++ resting ++ last`：
```go
pl.order = append(append(append(wReady, wBusy...), wResting...), wLast...)
return append(append(append(ready, busy...), resting...), last...), pl
```
  其中 `last` 是 `creditsLast`（`gateway/routing.go:1910`，Codex 用完免费额度但还能花 credits 的账号）。
- **与「沉底」的区别**：`resting`（冷却未结束）只排到「就绪之后」；`sink`（`gateway/sink.go:43`）是「429 尚有额度」的排到**所有未被限流过的人之后**，且记住沉底序号 `sunk.m[key] = sinking{now, sunk.n}`（`gateway/sink.go:36-40`），先沉者在前（`gateway/sink.go:94-118` `sinkOrder`）。勾选条件 `gateway/sink.go:87-89`：
```go
func sinks(on bool, routing string) bool {
	return on && !goesRound(routing) && routing != provider.Manual
}
```

### A.3.3 语义三：同 provider 多账号优先于 fallback 模型

- **注释** `gateway/fallback.go:10-13`（原文）：
```
// A provider with several keys on is several candidates, one per key, in
// order, and so is a subscription with several accounts on: when one
// account runs out, the next account of the same provider takes the
// request before any fallback model does.
```
- **实现**：`gateway/fallback.go:558` `planPaused` —— 先 `out := add(p, model, false)`（`gateway/fallback.go:582`，本 provider 的全部 key/account 先全展开），**之后**才 `for _, id := range p.Fallback`（`gateway/fallback.go:589`）追加备用模型。所以结构上「同 provider 全部候选」天然在「备用模型」之前。
- **账号展开**：`gateway/fallback.go:344` `accountsOn(p, model)` —— 用户顺序，`LoginRanks` 参与（`gateway/fallback.go:355-362`）；`keepLoginAs` 时登录中的账号按它自己的位次而非首位（`provider/keep_login_as.go:40-45`）。
- **单 provider 内并发门**：`gateway/fallback.go:295` `keepAtOnce(n, out, aside)` —— `AtOnce` 设置把同时使用的账号限制为 n 个，其余打 `reserve = n` 标记（`gateway/fallback.go:320`），并保留位次。

## A.4 用量衰减 `usageHalfLife`

**常量** `gateway/routing.go:39`：

```go
// usageHalfLife is how fast the tokens a key served stop counting against
// it when choosing by use: half of them after an hour.
const usageHalfLife = time.Hour
```

**算法**（明确的指数衰减，底数 2）`gateway/routing.go:56-63`：

```go
type tokenUse struct {
	n  float64
	at time.Time
}

func (u tokenUse) now(t time.Time) float64 {
	return u.n * math.Exp2(-t.Sub(u.at).Seconds()/usageHalfLife.Seconds())
}
```

即 `n(t) = n₀ · 2^(−Δt / 3600s)` —— **半衰期 1 小时的指数衰减**，不是线性、不是滑动窗口。

**累加方式** `gateway/routing.go:69-81` `served(rest, key, tokens)`：
```go
routed.used[rest] = tokenUse{routed.used[rest].now(now) + float64(tokens), now}
```
即「先把旧值衰到 `now`，再加本次 tokens，并把时间戳置为 `now`」。一次答对即 `delete(routed.failures, rest)`（计数清零）。

**只在按用量/按速度的策略里被消费**：`routes/routes.go:39` `Seat.Tokens`；`gateway/routing.go:2229` 填入 `Tokens: routed.used[c.restKey()].now(now)`；`gateway/routing.go:2242-2246` 仅当 `st.ByUse` 才把 `wg.tokens` 导出到 trace。

**速度的衰减是另一套**：`gateway/speed.go:24` `speedHalfLife = 20 * time.Minute`，`gateway/speed.go:29` `speedMost = 4096`，`gateway/speed.go:47-55` `decayed`/`fold` 用 `math.Exp2` 同样公式但半衰期 20 分钟，`gateway/speed.go:38` `speedStale = time.Hour` 之外视为「未测量」。

## A.5 组规则表（`Rule`）

## A.6 模式匹配入组（`*` 与 `re:`）

**定义** `provider/group.go:172-188`（`Group.Match` / `Group.Matched` / `Group.Placed`）：
```go

// over the "provider/model" id with * in it ("openrouter/*:free"), or
// a regular expression after "re:". Kept apart from Members, so the
```

**解析** `provider/groupmatch.go:29-79`：

```go
const RegexpPrefix = "re:"

func IsPattern(s string) bool {
	s = strings.TrimSpace(s)
	return strings.HasPrefix(s, RegexpPrefix) || strings.Contains(s, "*")
}

func compilePattern(p string) (*regexp.Regexp, error) {
	if re, ok := strings.CutPrefix(p, RegexpPrefix); ok {
		if strings.TrimSpace(re) == "" {
			return nil, fmt.Errorf("%q has no regular expression after %s", p, RegexpPrefix)
		}
		x, err := regexp.Compile("(?i)^(?:" + re + ")$")
		...
	}
	parts := strings.Split(p, "*")
	for i, s := range parts {
		parts[i] = regexp.QuoteMeta(s)
	}
	return regexp.Compile("(?i)^" + strings.Join(parts, ".*") + "$")
}
```
- `re:` → `(?i)^(?:<re>)$`，**必须整串匹配**，大小写不敏感（除规则内写 `(?-i)`）
- glob → `*` 变 `.*`（**`/` 也匹配**，不区分目录层级），其余逐字转义，整体 `(?i)^…$`
- 空 `re:` 报错；`IsPattern` 说「供应商模型 id 不含 `*`，所以 glob 不会被当成立 id」

**求解时机（非常关键）** `provider/groupmatch.go:118-132` `withMatches`：
```go
func withMatches(entries []Entry, g Group) Group {
	if len(g.Match) == 0 {
		return g
	}
	g.Matched = matchesIn(entries, g)
	g.Members = placedIn(append(slices.Clone(g.Members), g.Matched...), g.Placed)
	return g
}
```
注释 `provider/groupmatch.go:1-18` 明说：**模式从不写进 `Members`**，「每次读组就算一次（`groupsIn`）」，从「magpie 当前服务的模型」算，所以供应商新增模型自动进组、下架自动出组，**无需重新保存组**。
**唯一调用点** `provider/group.go:484`：`out = append(out, withMatches(entries, g.own()))` —— 即所有读取路径（网关路由、`/v1/models`、规则、Routing 页面、TUI、CLI）从同一处拿到组。

**求解细节** `provider/groupmatch.go:91-116` `matchesIn`：
- 只匹配「模型」，不匹配「组」
- 已按 id 命名的模型**不再被模式重复匹配**（`named` 集合）

## B.7 备用链与「仅在首字节前切换」

**aiworkgate 有**：`internal/gateway/dispatch.go:621-625`
```go
if res.streamed {
	releaseHeld()
	g.reportAttempt(winDecision, winDecision.PluginID, winPinned, rec, res)
	return
}
```
即「一旦上游开始流式返回，就不再重试/换号」。

**但它比 magpie 粗一档**：`streamed` 是「是否流式」的二元量，而不是「是否已经有正文到达 agent」。magpie 允许「reasoning / 只作框架的帧已流出、正文一个字都没说」时整体移交（`gateway/refusal_handover.go:15-19`、`60-63`、`69`）。aiworkgate 只要 `streamed` 为真就直接结束，**不会**再读「有没有说过话」。

# D. 缺口清单

## P0（不做则功能不可用 / 会造成线上事故）

### P0-1 冷却不分原因，且 402/余额耗尽**完全没有冷却**
- **magpie**：`gateway/routing.go:237` `creditRest = 30*time.Minute`，`:296` 阶梯到 7 天；`gateway/routing.go:238` `quotaRest = 15*time.Minute`；`gateway/routing.go:1433`/`:1453` 两个专分支。
- **aiworkgate**：`internal/scheduler/scheduler.go:572-615` 只有 `429` 与 `>=500/408/409/0` 两支；402 落 `default: 612-613`，**什么都不做**。
- **后果**：一个已把额度跑光的账号（Trae/A 类插件常见 402）会被**每个请求反复选中**，每次都被上游拒绝一次，形成稳定的一等公民级「浪费 + 延迟 + 上游风控风险」。
- **实施**：给 `Report` 增加 `why` 参数（原因由 dispatch 侧判定），新增分支：
```go
case status == 402:  // 或 reason == "credit"
    until := now + creditRestBase   // 30 分钟
    s.accountCD[key] = until
```
并把 `cooldown429Base/Max` 之外的原因也进表（quota / credit / verify / restricted / overload）。

### P0-2 没有「按顺序 / 用完再换 / 手动固定」三种最常用的路由模式
- **magpie**：`routes/strategies.go:201` `Ordered`（`Exact: true` 恒等序）、`:244` `Drain`（用完再换、不回头）、`provider/group.go:84`+`:101` `Manual`（只走 `Pick`）。
- **aiworkgate**：`internal/scheduler/scheduler.go:31-38` 六种里没有对应项；`fixed`（`:1560-1566`）是「按 `Priority` 升序」，仍会因冷却/软过滤跳过，**不是**「第一个用到不能答」。
- **后果**：用户无法表达「先把这个包月账号跑满，再动按量付费账号」（drain）、「严格按我排的序，不许越位」（order）、「这个池就固定在这个号上」（manual）。这三种是成本控制的核心手段。
- **实施**：新增三个策略值 + 在 `selectAccountLocked` 加分支：
```go
const (
	StrategyOrdered  = "ordered"   // 恒等序（按 Priority, ID）
	StrategyDrain    = "drain"     // 停在一个直到耗尽，换走不回头
	StrategyManual   = "manual"    // 只走 Pool.ManualAccountID
)
```
`Drain` 需要新增 `drainAt map[string]string`（pool → 当前账号 id）与「曾被拒为 credit/quota」的标记，对应 magpie `routes/strategies.go:205-240`。

### P0-3 组规则（`Rule`）完全缺失
- **magpie**：`provider/grouprule.go:46-106`（12 字段）+ `provider/group.go:219` `Rules []Rule` + `gateway/rules.go:191` `ruleFor` + `provider/grouprule.go:540` `MatchRule` + `:548` `ThenUses`。
- **aiworkgate**：全仓无对应结构。只有 `Pool.DefaultReasoning`（`scheduler.go:137`）与 `downgrade.go:28` `ApplyDowngrades`（`BackgroundDowgrade`/`LongContextDowngrade`，`:36-44`）两个**粗粒度**旁路。
- **后果**：任务书里要求的「按长度 / 带图 / 思考档 / agent / 时段」五类特征路由**一项都做不到**。长上下文不能自动切到大窗口模型，带图请求不能切到视觉模型，压缩请求不能切到便宜模型，高峰时段不能切到别家。
- **实施**：最小可行集先落 4 个条件（`tokens` / `images` / `effort` / `agents`），先不做 `intent`（要分类模型）与 `folders`（需要解析请求里的 cwd）。结构：
```go
type Rule struct {
	Use          uint64   // 账号索引
	More         []uint64
	UseEffort    string
	Tokens       int
	Images       bool
	Effort       string
	Agents       []string
}
```
匹配逻辑照 `provider/grouprule.go:503-537` 逐条移植；「首条匹配即定」照 `:540`；trace 照 `gateway/rules.go:26-79` 精简到 6-8 个字段即可。

### P0-4 模式匹配入组（`*` / `re:`）缺失
- **magpie**：`provider/group.go:177` `Match []string`；解析 `provider/groupmatch.go:29-79`；求值每次读组重算 `:118-132`，调用点 `provider/group.go:484`；手排 `Placed`（`:188`、`:134`）。
- **aiworkgate**：`Snapshot.Bindings[logical].Items` 是**静态** `[]Source`（`scheduler.go:156-161`），由管理端写死；`resolveModel`（`:1016-1048`）只做 id 解析。
- **后果**：插件新增模型 / 下架模型后，组不会自动跟随；每次目录变动都要人手动改绑定。这是「分组」最主要的运维痛点。
- **实施**：`Binding` 增加 `Match []string` 与 `Placed []string`；在 `resolveModel` 里把 `Match` 对「当前已安装插件的模型目录」求值后拼到 `Items` 之后。globs/regex 逻辑可直接抄 `provider/groupmatch.go:43-79`（无外部依赖，只用 `regexp`）。

### P1-7 切换粒度是 `streamed` 二元，不是「正文未开始」

## F.2 三条必须守住的架构约束

1. **不要让 `p2c` / hedge / 并发上限 / 熔断 被 magpie 的移植冲掉**。magpie 的 `Smart` 是「确定性排序」，`p2c` 是「随机采样两个取优」——两者可以并存（`p2c` 的输入 `scores` 可以换成 magpie 的 `Smart` 位次），但**不能替换**。同理 hedge 是 magpie 完全没有的能力。
2. **`Exact` 语义要显式建模**。magpie 用 `Strategy.Exact bool`（`routes/routes.go:172-176`）区分「顺序即结论」与「顺序只是偏好，下游还可按 `keyFit` 微调」。aiworkgate 没有这个概念，`fixed`/`ordered`/`drain`/`manual` 必须是 Exact，否则会被后续排序破坏。
3. **trace 字段先行**。magpie 的 `Weighed`/`weighing`/`RuleHit` 之所以可移植，是因为每个决策都有结构化输出。建议先把 `Decision` 扩成：
```go
type Decision struct {
	PluginID, AccountID, Model, LogicalModel string
	Sticky     bool
	StickyWhy  string   // 对齐 affinity.Why
	Strategy   string
	SeatRank   int      // 在这次排序里的位次
	SeatInputs []string // "urgency=0.83","ratio=0.71","latency=0.4"
	RuleN      int      // 命中的组规则，0 无
	Reasons    []string
}
```
先落字段，实现再追。

## F.3 不要照抄的部分

- **magpie 的 22 种 `Why`**：其中 10 种依赖供应商专有话术（`zhipuImageRefusal`、`openRouterSharedPool`、`codeAassistModelMissing`、`zcodeTrialBlocked`、`clineBackIn`、`regionWords`）。建议先移植 **8 种通用**：`credit` / `quota` / `rate` / `other` / `auth` / `proxy` / `offline` / `overflow`。
- **magpie 的组嵌套**（`Group.Members` 里写 `group/<id>`，`gateway/fallback.go:718` `planLevel` 递归 `depth`）：aiworkgate 的 `Binding` 目前只有一层，强行加嵌套会把 `resolveModel` 变成图遍历。建议**一期不做**。
- **magpie 的 `Manual` 全组挂起语义**：`provider/group.go:101-121`。aiworkgate 已有 `AccountConcurrency=0` 与 `Members` 二值，可先用「Manual 只走一个账号 + 跳过冷却过滤之外的排序」近似。

# G. aiworkgate 反而更强的地方

> 本节为避免单方面贬低，逐条给证据。

## G.1 `p2c`（power-of-two-choice）—— magpie 完全没有
- **aiworkgate**：`internal/scheduler/scheduler.go:1893-1907`
```go
func p2cIndex(scores []float64, r1, r2 float64) int {
	n := len(scores)
	if n <= 1 { return 0 }
	a := uniformIndex(r1, n)
	b := uniformIndex(r2, n)
	if a == b { b = (b + 1) % n }
	if scores[b] > scores[a] { return b }
	return a
}
```
- **magpie**：`grep -ri "p2c"` / `"power of two"` / `"power-of-two"` 在 `internal/` 下**零命中**。它的 11 种策略全部是**确定性排序**（`routes/strategies.go` 与 `routes/fastest.go` 全是 `sort.SliceStable`）。
- **意义**：确定性排序在账号数 > 2 时会在「前几名几乎等价」的情况下死盯第一名（造成热点）；`p2c` 用两次采样把 O(n) 查找降到期望 O(1) 且天然分散。**这是 aiworkgate 的结构性优势，检索口径应保留为「对方没有」**。

## G.2 首字节对冲（hedge）—— magpie 完全没有
- **aiworkgate**：`internal/gateway/dispatch.go:36` `hedgeHeader`、`:591` `hedgeMS = pool.HedgeMS`、`:506-540` `hedgedAttempt`、`:905-1040` `prepareHedge`/`finishHedge`/`closeHedgeLoser`；`Pool.HedgeMS`（`scheduler.go:136`，范围 `minHedgeMS=1000`..`maxHedgeMS=8000`，`internal/webui/scheduler.go:30-31`）
- **magpie**：`grep -ri "hedge"` 在 `internal/` 下**零命中**。它只有串行 failover（`gateway/fallback.go:3-9`「the next one only while none of the reply has been sent」）。
- **意义**：对冲是延迟优化的最强手段（尾部延迟），magpie 文档里看不到任何并行尝试。

## G.3 账户级并发上限 + 满则选最少在途
- **aiworkgate**：`internal/scheduler/scheduler.go:1402-1537` `evaluateAccountsLocked` —— `Pool.AccountConcurrency`（`:133`）> 0 时先筛「在途 < 上限」，全满则取 `minLoad` 的那批（`:1516-1530`），并在 `Reasons` 写 `"all accounts at concurrency limit; least loaded"`（`:1318-1319`）。配合 `sticky yield`（`:1279-1287`）。
- **magpie**：最近的对应物是 `gateway/fallback.go:295` `keepAtOnce`（`AtOnce` 限制**同时使用**的账号数），语义是「防同一 IP 多号被封」，**不是吞吐限流**；全池饱和时它没有「取最少在途」这一层。
- **意义**：并发治理是生产必需的，aiworkgate 在这块更完整。

## G.4 池级熔断
- **aiworkgate**：`internal/scheduler/scheduler.go:604-610` —— 同 `pool` 连续 `circuitThreshold=3` 次（5xx/408/0）→ `circuitSeconds=60` 熔断；`circuitOpenLocked`（`internal/scheduler/scheduler.go:516`）在 `plan` 开头就拦（`:1180`）。
- **magpie**：**未找到** pool/供应商级熔断。它的等价能力是「单 key 的 rest + 后台探测」（`gateway/rest_probe.go:3-15`），粒度是**一个 key**，不是**一个供应商**。
- **意义**：供应商整体挂掉时，熔断能省掉每请求一次必败的上游调用；magpie 靠每个 key 各自 rest 来近似，成本更高。

## G.5 冷却持久化更完整
- **aiworkgate**：`internal/store/store.go:454-463` 表 `scheduler_cooldowns(plugin_id, account_id, model_id, until, reason, strikes, updated_at)` + 索引 `idx_scheduler_cooldowns_until`；`RestoreCooldowns`（`internal/scheduler/scheduler.go:624`）连 `strikes` 一起恢复，重启后 429 继续翻倍；写盘是 debounce 批处理（`cooldownPersistDelay=500ms`、`cooldownPersistBuffer=256`，`scheduler.go:368-371`）**不阻塞请求路径**。
- **magpie**：只持久化 `creditLadder` 那类 rest（`gateway/rest_store.go:15-20`），写 `rests.json` 整文件；注释明确「其他的一分钟到几小时……重新读一次就找到了」——这是**有意的取舍**，但在「供应商给的时间很长」这类场景（如 8 天配额冷却）重启后会丢。
- **意义**：aiworkgate 的持久化模型更适合重启频繁的宿主。

## G.6 粘性绑定用 SQLite 而非 JSON 文件
- **aiworkgate**：`internal/store/store.go:323-330` 表 `sticky_bindings(scope, key, plugin_id, account_id, expires_at)`，`PRIMARY KEY(scope, key)`；读写 `internal/store/sticky.go:13`/`:37`/`:75`。
- **magpie**：`affinity.json` 整文件（`gateway/affinity.go:283` `sticksPath()`），上限 `sticksKept = 512`（`:81`），注释说明「超出就按时间淘汰」。
- **意义**：SQLite 可按 scope/时间查询、可统计、可运维导出；JSON 是 512 条上限的滚动文件。

## G.7 降级（downgrade）机制 magpie 无对应概念
- **aiworkgate**：`internal/scheduler/downgrade.go`（实际文件名 `downgrade.go`）`ApplyDowngrades`（`:28`）—— 两个规则：`background`（`MaxTokens<=128` 且 `PromptChars<=512`，`:36-38`）、`long_context`（`EstimatedTokens>=100000`，`:43`）；`flashAlternative`（`:83-101`）按「显式 flash 名」或「multiplier 至少减半」选更便宜的模型；输出 `X-Aiworkgate-Downgraded` 头。
- **magpie**：**未找到**「按请求特征自动降级到便宜模型」的机制。它的对应物是组规则 `Compact`（`provider/grouprule.go:82`）与 `Cheapest` 模式（`routes/strategies.go:556`），但都是**路由到别处**，不是**改请求的模型名**。
- **意义**：后台任务与长上下文降级能直接省钱，这是 aiworkgate 的设计优势。

## G.8 `interpretation` / 解释接口
- **aiworkgate**：`Explain`（`internal/scheduler/scheduler.go:1131`）+ `Explanation`（`:257-262`）+ `traceCandidates`（`:1629`）—— 每个被拒候选都有 `Reason`（如 `"account cooldown until 1730..."`、`"credits depleted"`、`"not a pool member"`），能直接展示「为什么没选它」。
- **magpie**：有 `Weighed` / `RuleHit`（同样强），但**没有**「被拒候选的逐条原因」聚合接口；拒绝信息散在 `pl.left`/`pl.held`/`pl.capped`/`pl.unlisted` 四个桶里（`gateway/fallback.go:558-580`）。
- **意义**：两个都有 trace，但 aiworkgate 的 `Explain` 是**单一响应、扁平列表**，更适合 UI 直接渲染。
