aiworkgate **没有 IR**。它是「入站结构与 Chat 结构之间的一次性转换」：

| 转换 | 文件:行号 |

| Chat →（直通插件） | gateway.go:634 → dispatch.go:421 `forwardScheduled` |

| Anthropic → Chat | anthropic.go:53 `chatBodyFromAnthropic`、99 `anthropicMessages`、334 `anthropicTools` |

| Chat → Gemini（上游） | upstream_gemini.go:45 `chatToGeminiRequest` |

后果：**每次转换都是「有损」的**。magpie 的 IR 能保证「Chat 客户端 ↔ Anthropic 上游 ↔ Responses 客户端」三段往返不丢 sealed 推理、不丢 `tool_use` 配对、不丢 `cache_control` 断点；aiworkgate 每条路径单独写一次转换，只能在单条路径内做局部补偿：

- aiworkgate 对 `thinking` 的信号只保留字符串：`anthropic.go:41 thinkingSignature(text)`（从文本里抠 `signature`），而不是结构化字段。
- aiworkgate 对 `redacted_thinking` 无对应概念（全库检索 `redacted_thinking`、`encrypted_content` 无匹配）。

### 2.2 `Requested` vs `Served`：aiworkgate 只有前两段，缺第三段

magpie 的三段语义（trace.go:173-178 与 Try 的 460-466）：

| 段 | 含义 | magpie 字段 |
|---|---|---|
| ① 客户端请求 | 客户端在 `model` 字段里写的 | `Route.Model`（trace.go:83） |
| ② 实际投递 | 路由/降级后真正发出去的 | `Try.Model`（trace.go:429） |
| ③ **上游应答** | 上游回复体里说「我是谁」 | `Route.Served` / `Try.Served` |

aiworkgate 现状：

| 段 | aiworkgate 字段 | 文件:行号 | 说明 |
|---|---|---|---|
| ① | `rec.model` | gateway.go:325、prepareRecord 1114 | 客户端写的 |
| ② | `rec.model` 被改写成 physical | dispatch.go:524、`prepareBody` dispatch.go:1340-1371（`top["model"] = rawModel` 1357） | ✅ 有 |
| ② 的另一半 | `rec.logicalModel` | gateway.go:326、dispatch.go:524、892；来源 `scheduler.Decision.LogicalModel`（scheduler.go:237、1307） | ✅ 有逻辑名 |
| ③ | **不存在** | — | ❌ |

**证据（③ 缺失）**：

1. `dispatch.go:1166-1251 deleliver` 只读 `resp.StatusCode`、`resp.Header`、body 字节流；`tap.finish()` 只解析 usage（tap.go:216 `parseUsage`、135 `parseUsageTail`），**不解析响应体的 `model` 字段**。
2. `envelope.go:768`、`793` 构造回包时写的是 `firstNonEmpty(clientModel, reply.Model)` —— 即**向上游回写的是客户端要的模型名**，而不是上游声明的名字；因此即便上游换了模型，客户端与日志都看不到。
3. `model.APIRequestLog`（model.go:394-419）只有 `Model`、`LogicalModel`，无 `Served`/`Swapped`/`Upstream`。
4. `store` 侧 `api_logs.go:74-79`（`apiLogColumns`）落库字段同样只有 `model`、`logical_model`。

**后果**：magpie 能回答「这个请求被换到了哪个模型、是不是聚合商背后还有一层（`Upstream`）、是不是另一个 magpie 的路由组（`Routed`）」，aiworkgate 三个都答不了。这与 magpie 明说的痛点一致（trace.go:36-42 的注释：没有 `Moved` 时一行读起来像「客户端要了 A，实际给了 B」而说不出原因）。

**关键事实：脱敏只发生在「写日志」这一步，不发生在「发给上游」这一步。** 检索依据：`grep -rn "redact\|Redact\|mask\|Mask" --include=*.go internal/gateway/ | grep -v _test` 只命中 `custom_models.go:435/443 redactSecret`（把**上游自己的** key 从错误消息里抹掉）、`egress_hint.go:192 redactUserinfo`（隧道文本里的 `user:pass@`）。请求体在 `dispatch.go:421 forwardScheduled` / `prepareBody` 之后**原样**发往上游。

即：**用户的 prompt、工具结果、文件内容、数据库连接串，全部明文出境。**

### 3.3 magpie 的三层脱敏架构（必须按层搬）

magpie 把「脱敏」分成三个**不同可靠性等级**的层，这是设计的核心，不能合并：

| 层 | 目的 | 是否可还原 | 失败策略 | 实现 |
|---|---|---|---|---|
| **① 对外替换（Mask）** | 发给第三方厂商前把值换占位符 | ✅ 必须还原 | **fail-closed**（脱敏要开但没 masker / masker 报错 → 请求不出门） | `gateway/redact.go:26-75 redactedHits`、`gwmw` 包注释 gwmw.go:1-16 |

| **③ 落盘擦除（Scrub）** | 日志/归档/错误消息里抹掉，**永不还原** | ❌ | 尽力而为 + memo 缓存 | `redact/scrub.go:35 Scrub`、`194 ScrubJSON`、`142 ScrubHeader`、`29 SecretName`、`20 Scrubbed="[REDACTED]"`、`20 scrubbed()` → `[REDACTED:KIND]` |

#### P0-2 · 回程还原（SSE 占位符还原）缺失

**现状**：即便补上 P0-1，所有上游回复都会把 `{{EMAIL_xxxxxxxx}}` **原样**交给客户端，模型/工具链会拿到假值。aiworkgate 没有任何 `Writer`、`Restore`、`partialTail` 概念（`grep -rn "placeholder\|restore\|Restore" --include=*.go internal/ | grep -v _test` 只命中无关的 `RestoreCooldowns`、`resetRulePack`）。

**为什么单列 P0**：只做 P0-1 会让产品**更坏**——占位符漏进客户端上下文，跨轮对话彻底污染；且流式场景下「半个占位符」会切断 SSE 帧（magpie `writer.go:337-372 splitEvent` + `redact.go:1749 partialTail` 就是为这个）。

**magpie 依据**：`redact/writer.go:19-405`（`Writer`/`decide`/`Write`/`Finish`/`event`/`splitEvent`/`commentLines`/`eventEnd`/`held`）。

#### P0-3 · 客户端 Key 无有效期、无签发者约束

**现状**：`model.ClientKey`（model.go:333-350）只有 `ModelScope/BindPool/DailyQuota`；`secrets/clientkey.go:35-46 NewClientKey` 不写 `Expires`；`store/client_keys.go` 表无过期列；`webui/keys_scope.go:113 createClientKey` 无 TTL 入参。

**后果**：key 泄漏 = **永久**有效，直到人工删除。magpie 的 `access/issue.go:16-23` 注释把场景写得很具体（沙箱 agent 各一把、自己失效）。配合 P0-4（LAN 下 `/v1` 只验 key），这就是「一次泄漏 = 无限期可用的上游额度」。

**magpie 依据**：`access/issue.go:26-29 MinTTL/MaxTTL`、`49-77 Issue/Issued`、`81-... IssueKey`、`access/access.go:163-171 Expires/Issuer/Issues`、`key_limit.go:36 keyLimited`。

#### P0-4 · IP 白名单缺失

**现状**：`ListenLAN=true` + 有 LAN 密码 → `0.0.0.0`（app.go:392-397）；`/v1/*` 只验 key（app.go:829 + gateway.go:524-530）。全库 `grep -rni "allowip\|allow_ip\|whitelist" --include=*.go internal/` **无匹配**。

**后果**：与 P0-3 叠加成「一台机器泄漏一把 key，全网段可用」。

**magpie 依据**：`gateway/allow.go:1-230`（尤其 `104 peerAddr` 只认 `RemoteAddr`、`84 allowPrefixes` 笔误不放行、`66-74` 读不到设置时降级为只许本机）、`settings/allowips.go:19-64`、`lan.go:435`（**在 key 之前**）。

#### P0-5 · CORS 通配符 `"*"` 被放行

**现状**：`config/config.go:417-419` 显式 `if origin == "*" { continue }`（跳过校验），`gateway/gateway.go:576-578` 对 `"*"` 回显请求 Origin。

**后果**：任意网页可通过预检并携带 `Authorization` 读 `/v1` 回复；配合「前端把 key 存在可被同源网页读取的位置」即 key 外泄。magpie 的取向相反且写进错误文案（`settings/origins.go:38-40`）。

**magpie 依据**：`settings/origins.go:38-40`、`gateway/cors.go:46-52 foreignPage`、`53-71 Origin:null / localhost 子域`。

#### P0-6 · 路由追踪只有「决策理由」，没有「执行事实」

**现状**：
- 无 `Try` 链：`retry` 只有 `dispatch.go:284-316 logRetry` → `schedLog.Info`（宿主日志一行）。
- 无 `Served`：`deliver`（1166-1251）不读响应体的 `model`；`envelope.go:768/793` 回包写 `clientModel`。
- 无 `Swapped / Routed / Upstream`。
- 无 route-events 流、无 trace API。
- `scheduler.Explanation`（scheduler.go:257-262）只在 `prepareHedge`（dispatch.go:905-912）用一次。

**后果**：用户问「为什么这次换账号/换模型了」「上游到底谁答的」，系统答不出；审计与计费争议无凭据。magpie 把这条做成了 `Trace` 页（trace.go:16-42 注释即其动机）。

**magpie 依据**：`trace.go:48-195 Route`、`426-521 Try`、`route_events.go:33-60`、`917-935 gatewayTrace`。

## 9. 实施建议

### 9.1 顺序（每步独立可验收）

1. **P0-3 + P0-4 + P0-5**（访问安全三件，~2 天）：加 `expires_at/issuer_id` 列 + IP 白名单中间件 + 拒 `*`。纯增量，无行为回归风险；先把「泄漏即永久」和「通配 CORS」两个洞堵上。
2. **P0-1 层③升级**（~2 天）：把 `logging/redact.go` 换成 `Scrub/ScrubJSON/ScrubHeader` 全量版 + 71 个反例。日志先安全，上游链路后动。
3. **P0-1 层① + P0-2 层②**（~5-8 天）：引入 `redact` 引擎 + `gateway/redact.go` 的 fail-closed 接线 + `writer.go` 回程还原。这一步必须带开关（config 新增 `privacy.enable`），默认关，测试全绿后默认开 `Secrets=true Personal=true`、其余 Category 按默认表。
4. **P0-6**（~3 天）：`reqRecord` 加 `served/swapped/tries`；`deliver` 抓 `model`；`api_logs` 表加列；`logRetry` 从 logger 改为落库挂请求行。不做 route-events 流（可后置 P2）。
5. **P1 按需**：P1-7（PII 类别开关 UI）、P1-8（Origin 规范化）、P1-9（限速）、P1-10/P1-11（Key 增强）先行；P1-1 ~ P1-6（协议面）与 P1-12 ~ P1-14（插件）看产品需要。

### 9.2 关键取舍

- **不要一次把 19 个 kind 全开**。magpie 自己都把 `home/userhost/ip/bucket` 默认关（more.go:48-52），因为误掩路径/主机名会打断工具调用。首发只开 `Secrets` + `personal`（EMAIL/PHONE/ID_CARD/BANK_CARD 四类是 `Personal` 一并带的）。
- **`MaskJSON` 的 `signed/args/defs` 三分类必须实现**，否则 Anthropic 的 thinking 签名、Gemini 的 thoughtSignature、工具回放全会 400（json.go:393-398 注释的三个真实案例）。aiworkgate 已有对应概念雏形：`dispatch.go:173 isThinkingSignature400`——说明已经撞过这堵墙。
- **`writer.go` 的 `asIs` 分支不能省**：二进制响应（audio/image/pdf）被当文本还原会把文件打碎。
- **`redactedHits` 的 fail-closed 语义不能放宽**：脱敏开了但引擎抛错 → 请求不出门（gateway/redact.go:22-25 注释原文「masking wanted with no masker serving, or a masker that fails, is an error, and the request goes nowhere」）。
- **评估即验收**：搬完后 `go test ./internal/redact -run TestMaskEval` 必须全绿；任何「为过测试放宽规则」的改动必须同时加反例。
