## 2. magpie 侧规格：请求页的分页 / 缓存 / 失效

`request_page.go:1-6` 的头部注释就是规格：

> 「请求页保留**紧凑的按来源记录，不是第二份完整账本**。未变的来源永不再次解码。聚合在流上做；**只有被请求的那一页会被物化/排序**。导出仍可以显式要完整账本。这个缓存是可丢弃的、有界的。」

### 2.1 缓存键 `pageKey`

`queryPageOf`（`request_page.go:895-1033`）：

```
q := pageKey{p, f, offset, limit, now.Format(time.DateOnly)}   // :923
```

**键 = (周期, 过滤条件, offset, limit, 当天日期)**。同一天同一个 offset/limit 直接命中。

三层缓存：
| 层 | 结构 | 位置 | 上限 |
|---|---|---|---|
| 页缓存 | `idx.pages map[pageKey]RequestPage` | `:924`、`:1021` | **16 页**（`:1021`） |
| 热力图页缓存 | `idx.heats map[pageKey]heatPage{page,version,at}` | `:928-931`、`:1026` | 16，且 `version` 必须相同、`time.Since(at) < heatFresh=30s`（`:744`） |
| 飞行中合并（single-flight） | `idx.flights map[flightKey]*pageFlight` | `:933-951` | 同 `(key,q)` 的并发请求 `<-fl.done` 等同一份（`:935-937`） |

### 2.2 失效条件：`meta` 与 `key` 两级

`requestState`（`request_page.go:801-809`）注释（`:793-800`）说得很清楚：**meta 变 → 掉 chunk；key 变 → 掉 page。**

- `meta`（`:824`）= agent 身份 + 供应商重命名 + `ModelPrices` + `Wires` + `usage.jsonl` 的 stat + catalog cache 的 stat + 客户端 agent 别名 + 清空标记；
- `key`（`:825-851`）= `meta` + 日志快照 version + 当地日期(`2006-01-02 MST`) + Codex 线程身份哈希（`:857-876`，按 key 排序后 uvarint 编码，避免每次多 MB 的 JSON）+ 每个会话文件的 `path:size:mtime` + 其它电脑的天。

**关键设计**：Codex 线程身份只进 `key` 不进 `meta`（`:796-800`），否则每来一个新 Codex 线程（含 subagent）就掉全部 chunk，下一次读要把整段历史重读。

### 2.3 chunk 级复用 + 有界回收

- `idx.chunks map[path]*rowChunk`：同名文件 size/mtime 没变就不重新解码；
- `adopt`（`:1358`）/ `private`（`:1416`）/ `keep`（`:1426`）/ `noteBuilt`（`:1461`）/ `save`（`:1485`）；
- 内存上限：`requestCacheBytes = 128MB`（`:768`）、闲置 2 分钟后压到 `requestIdleBytes = 24MB`（`:769-770`），由 `keepWhileAsked`（`:1520-1530`）的 `time.AfterFunc` 触发；
- `trim`（`:1536-1560`）按「最近使用」排序后删到界内；
- 落盘：`requests-v1.bin`（`request_disk.go:39` `requestDiskMagic = "magpie-requests-v1\n"`），一条 entry = 长度 + CRC32 + 字节，坏的 entry 终止读、之前的仍有效（`request_disk.go:15-25`）。
- `limit` 上限 `min(limit,500)`、`limit<=0 → 100`（`:896-899`）。
- 内存布局：`packedRow` 216 字节（`request_page.go:69-93`），时间用 `int32` ms（`:83-89`），token 用 `int32`（`:78-80`），zone 用 `uint16` 索引表（`:102-155`）—— 因为 `*time.Location` 指针会让 GC 扫每一行。

### 2.4 「只物化当前页」

`buildRequestBlocksIn`（`:2420`）→「聚合在流上做，只有当前页排序」。配套的 `cellPass`（`request_cells.go:25-31` 起）：每个 chunk 的「单元格」缓存按 5 个维度预先算好位掩码（`cellKeep` / `cellUncounted` / `cellVia` / `cellCharted` / `cellComputer` / `cellGroup` / `cellChart`，`:42-49`），新来一次调用只重算变化的 chunk；否则「420k 调用的 All 页每次刷新都要读全部历史，约 1s」（`request_cells.go:15-22`）。

## 4. magpie 侧规格：会话视图

`gateway_sessions.go`。要分清**两类会话**：

| 类 | 来源 | 是否在「Sessions」tab |
|---|---|---|
| Gateway session | 网关自己记录的调用（`session` 头） | 是 |
| 本地 session 文件 | 从 agent 自己的 jsonl 读出（`Source=log`） | 是（Sessions tab 的主体） |

### 4.1 切分

`GatewaySession`（`gateway_sessions.go:41-51`）：

```
Agent, ID, Start, Last, Models []GatewayModel, Daily []GatewayDayUsage, Tokens, Cost, Unpriced
```

- **身份 = `(agent, session id)` 二元组**：`gatewayKey struct{ agent, id string }`（`:381`）；`countGateway` 里 `k := gatewayKey{a, r.Session}`（`:449`）；
- 只有 `Session != ""` 的行才进会话（`:444-445`：`r.IsRejected() || r.IsReported() || r.Session == ""` 直接 `return`）；
- `nativeKeys map[string]bool`（键是 `agent+"|"+id`）用来**抑制与本地 session 文件重复的投影**（`:20-25`、`:450-451`、`:74`）；
- `Agent` 先过 `ReportedAs(...)` 归一（`:447`）。

### 4.2 跨 provider 归并

- 会话里**按模型聚成 `Models []GatewayModel`**（`GatewayModel{Model, Tokens, Cost, Priced}`，`:53-58`），不按 provider 分——因为一个会话可能被路由到多个 provider，归并口径是「这个会话一共用了哪些模型」；
- 按天聚成 `Daily []GatewayDayUsage{Date, Agent, Model, Tokens, Cost, Priced, first, last}`（`:27-36`），`first/last` 是为了「从某个午夜起看」时能直接从这一份投影切片（`:34`、`:124-160`），不建第二份；
- 「与本地文件重复」去重也在这里做，键同样是 `agent|id`。

### 4.3 增量与上限（性能规格）

- 全量投影只留**一份**（`gatewayCache`，`:214-218`）：「~600k 调用，每个区间若各存一份是 ~37MB，同时开 4 个」（`:206-213`）；
- `gatewayPrefix`（`:283-291`）+ `foldGateway`（`:259`）：日志的完整 block 永不变，所以「前缀」已算的部分不必重算，新调用只在前缀上续（`countGateway(blocks[pre.n:cut]...)` 与 `countGateway(blocks[cut:]...)`，`:315-322`）；
- `EachGatewaySession`（`:107-113`）：**不拷贝整个列表**，逐个回调——因为「Sessions 列表每轮轮询会把 ~10k 个会话全拷一遍」（`:101-106`）；
- `Models`/`Daily` 是投影自己的切片，用 `slices.Clip` 截断（`:112-113`、`:294`），调用方 append 时自然 COW。

### 4.4 「通过 vs 直读」三栏

`RequestPage.Through / Direct / Reported`（`request_page.go:43-50`）+ `usageapi.Ledger.Through/Direct/Reported`（`internal/usageapi/usageapi.go:271-278`）：`Sum` 是三者合计，页面并排显示，让读者分清「magpie 真carried 的」与「它只读到过的」。`SourceOf`（`ledger.go:107-110`）：被本地拒绝的和 probe 两者都不是。

## 5. magpie 侧规格：按服务模型拆分（served.go）

| 概念 | 字段 | 区别 |
|---|---|---|
| 请求的 | `Requested`（`req`） | agent 说出口的名字，可能是 alias / 组 / `plugin/model` |
| 发出的 | `Model` | magpie 真正发给上游的 id |
| 声明的 | `Served` | 厂商**回复里**的 model 字段 |
| 背后 | `Upstream` | 聚合商背后那家 |

**为什么要三栏**（`served.go:13-18` 注释）：厂商可能用**更便宜的模型**应答你请求的那个（忙时降级），而回复里会写出来。多数厂商把名字原样回显（可能带日期/固定版本尾巴）——那还是同一个模型；`Swapped()` 负责把「同一个模型不同写法」与「真换模型」分开。

`Row.Swapped`（`ledger.go:34`）在定价时结算一次并置位 `swapKnown`（`block_price.go:14`），读回时不再看第二遍两个名字（`request_page.go:430-432`）。

**计费影响**：`pricing` 优先按 `Served` 在同一 provider 有价时用它（`ledger.go:521`、`:547`）。

## 6. magpie 侧规格：按思考档拆分（effort_split.go）

- 数据来源：Codex 的 session 文件里 `ModelEffort{Model, Effort, Tokens, Reasoning, Cost, Priced}`（`internal/sessions/sessions.go:100-107`）；
- 入口：`CodexModelEffort(p Period)`（`internal/usage/codex_identity.go:595`），返回 `map[model][]ModelEffort`；
- 「切点前」的档位和热力图一样落盘：`effort-v1.json`（`effort_split.go:42-51`），条目 `{Key, Cut, Since, Sums}`；
- 同时最多留 `effortDiskPeriods = 4` 个周期（`:58`）——曾因 All 与 overview 的周期互相覆盖，每次启动都要重算几天（`:53-57`）；
- `effortSplit`（`:124`）：`cut = today - heatRecent`（=2 天）；`settled`/`recent` 用 `splitAt`；`heatBefore(cut, recent)` 做「最近 chunk 里 cut 之前的行」的指纹，**任何变化都会让旧档位作废**；缓存新鲜度 `heatOldFresh`（10 分钟）；
- 三级回退：内存 `effortOlds[p]` → 磁盘 `effortDiskRead` → 增量 `effortAdvance`（`:226`）→ 冷启 `effortCold`（`:199`）；都不行才全量配对 `full()`。

**用途**：同一模型在 `low/medium/high` 档的 token/成本/延迟分账 —— 这是 magpie 唯一做「思考档」的地方，且只在 Codex 侧。

## 7. magpie 侧规格：冷热拆分（cold_split.go）

**这不是用户可见的功能，是性能实现**——这点必须先说清，否则会误判成「功能缺口」。

- 头部注释（`cold_split.go:10-18`）：首启无落盘时，如果一次性配对全历史，「~210MB / ~355MB 活堆 / 一年历史 ~500MB footprint」；
- 解决：`coldSpan = 4`（`:23`），按**4 天一段**配对历史，每段配完就释放，再配下一段；
- `coldSpans(since, cut, sets, fn)`（`:34`）：按 chunk 的 `first`/`Latest` 与 `[lo, hi] = [span-48h, span+48h]` 求交，只把够得着的 chunk 拿进这一段；
- 未定价的网关块**只为这一段定价**（`b.alone()`，`:67-74`），段结束 `b.release()`（`:88-90`）。

**真正的「冷 / 热」判据**是：`cut = today - heatRecent(2天)`，`cut` 之前 = 已settled（可落盘复用），之后 = recent（每次重配）。`heatReach = 48h` 是「一段能碰到前后多远」。

## 9. magpie 侧规格：窗口占用历史（window_holds*.go）

**这是 magpie 最有意思的一块**：由「已路由的调用」反推「整个套餐窗口一共多少」。

- 目标（`window_holds.go:3-8`）：账号卡片给出每个窗口用了百分之多少（厂商读数），magpie 知道自己从这个窗口开始路由了多少，于是**整窗 ≈ 已路由量 / 百分比**；
- 只在诚实的地方算（`holdsBounds` `:71-92`）：有 `Error`/`From`/`User==""`/`Balance` 直接不告诉；`w.Used < provider.HoldsFloor` 不给（置信度不够）；时钟未知（`HoldsNoClock`）；`Unlimited`/`Aside`/`Family`/`Pool` 各有规则；
- 「干跑」`dryRun`（`:99-103`、`:105-160`）：某个窗口读数见底的那一段，回答的调用可能是走 credits/额外额度付的，日志里看不出来——这类调用要从「窗口占用」里排除；
- 输出 `provider.WindowHolds{Tokens, Cost, Priced, Used, Routed{Calls,Tokens,CacheRead,CacheWrite,Cost}, ...}`（`internal/provider/window_holds.go:23-35`）；
- **历史推算** `HistoricalWindowHolds(cards, hist, from, to)`（`window_holds_history.go:15`）：用**当时那次读数的记录边界**（`last.Start`/`ResetsAt`），不是今天的百分比；返回的卡片每张只带一个窗口（因为各窗口的采样时刻不同）；短窗口取「最后一个观测周期」，不是所有周期相加（`:7-11`）；
- HTTP：`GET /api/usage/quotas/history`（`internal/gui/usage.go:377`）、`GET /api/usage/quotas/history/holds`（`:387`，要求 `provider`、`user` 与一个**已结束**的时间段）；
- 接入点：`init() { provider.ReckonHolds = WithWindowHolds }`（`window_holds.go:24`），于是 `magpie quota --json` 与 `GET /v1/magpie/quotas` 和 Usage 页说同一个数（`:22-23`）。

## 16. 实施建议

### 建议 1（先做，P0 三件套，一次迁移打包）

一次 `store.go` 版本迁移 + 一次 `tap.go` 采集扩展，把 P0-1/P0-2/P0-3 一起落地，避免三次改表：

```sql
-- v6: api_logs 补三模型 + 缓存四栏 + 思考 + 拒绝/尝试
ALTER TABLE api_logs ADD COLUMN model_requested TEXT;   -- P0-1，agent 请求的
ALTER TABLE api_logs ADD COLUMN model_upstream  TEXT;   -- P0-1，实际发给上游的 physical
ALTER TABLE api_logs ADD COLUMN model_served    TEXT;   -- P0-1，回复声明的
ALTER TABLE api_logs ADD COLUMN model_swapped   INTEGER NOT NULL DEFAULT 0;
ALTER TABLE api_logs ADD COLUMN cache_write     INTEGER NOT NULL DEFAULT 0;  -- P0-2
ALTER TABLE api_logs ADD COLUMN cache_write_1h  INTEGER NOT NULL DEFAULT 0;  -- P0-2
ALTER TABLE api_logs ADD COLUMN cache_unknown   INTEGER NOT NULL DEFAULT 0;  -- P0-2
ALTER TABLE api_logs ADD COLUMN reasoning_tokens INTEGER NOT NULL DEFAULT 0;  -- P1-1
ALTER TABLE api_logs ADD COLUMN cost_usd        REAL;                        -- P0-3
ALTER TABLE api_logs ADD COLUMN pricing_model   TEXT;                        -- P0-3
ALTER TABLE api_logs ADD COLUMN rejected        INTEGER NOT NULL DEFAULT 0;
ALTER TABLE api_logs ADD COLUMN tries           INTEGER NOT NULL DEFAULT 0;  -- P1-5
```

采集侧三个插入点（都在现有代码里，改动小）：

| 插入点 | 文件:行 | 动作 |
|---|---|---|
| 请求侧模型 | `internal/gateway/gateway.go:321-351`（`reqRecord`） | 在 `rec.model = routed`（`:918`/`:1007`）**之前**存一份 `rec.modelRequested`；`dispatch.go:454` 改写时保留 |
| 上游 physical | `internal/gateway/dispatch.go:535`（`decision.Model = physical`） | `rec.modelUpstream = physical` |
| 回复侧 served | `internal/gateway/tap.go:238-249`（`apply`） | 若 `usageCounts` 补 `Model string` 字段，从回复 `model` 抄；或在 `envelope.go` 的响应改写处抄 |

`tap.go` 的 `usageCounts`（`:172-186`）补两个字段即可接住已有结构：

```go
CacheCreationInputTokens int64 `json:"cache_creation_input_tokens"` // envelope.go:50 已有同名
CompletionTokensDetails *struct{ ReasoningTokens int64 `json:"reasoning_tokens"` } `json:"completion_tokens_details"` // envelope.go:46 已有
```

### 建议 2（分页缓存，P1-6）

不抄 magpie 的 chunk 机制（SQLite 行已经紧凑），只抄它的**三层结构**：

1. **页缓存**：`map[cacheKey][]model.APIRequestLog`，键 `(from, to, plugin, group, account, model, page, page_size, today)`，上限 16 条，与 `request_page.go:923`/`:1021` 一致；
2. **单飞**：同键并发用一个 `chan struct{}` 等（`request_page.go:933-951`）；
3. **新鲜度**：`time.Since(at) < 30*time.Second`（`request_page.go:744` 的 `heatFresh`）。

翻页的 `OFFSET` 深扫问题另修：加覆盖索引 `(ts, id)`（`api_logs` 已有 `idx_api_logs_ts_source`，`store.go:362`，但 `UsageSessions` 是 `ORDER BY ts DESC, id DESC`，需要 `(ts DESC, id DESC)` 或改用 keyset 翻页 `WHERE (ts,id) < (?,?)`）。

### 建议 3（会话聚合，P1-2，**不要和"会话明细"混淆**）

`Usage.vue` 的 `sessions` tab 保持（它是逐请求列表，有用）；**新增**一个「按会话」视图，走新接口 `GET /api/usage/sessions/aggregate`：

```
SELECT conversation_id, source, account,
       COUNT(*) requests, SUM(prompt_tokens), SUM(completion_tokens),
       SUM(cache_write), SUM(cached_tokens), SUM(cost_usd),
       MIN(ts) start, MAX(ts) last,
       COUNT(DISTINCT model) models
FROM api_logs
WHERE conversation_id <> '' AND <filter>
GROUP BY conversation_id
ORDER BY SUM(prompt_tokens+completion_tokens) DESC
```

字段照 `gateway_sessions.go:41-58` 的 `GatewaySession`，但去掉 `nativeKeys`（aiworkgate 没有 agent 的 jsonl 来源）。`conversation_id` 目前靠客户端传（`internal/gateway/dispatch.go:1399-1405`），需要先确认哪些客户端真的传——`Logs.vue` 已把它作为一列展示，说明至少有值。

### 建议 4（热力图，P1-3）

完全不需要抄 magpie 的 `heatmapPeriod` 分支。一条 SQL 就够：

```
SELECT day,
       SUM(requests) calls,
       SUM(prompt_tokens+completion_tokens+cached_tokens) tokens,
       SUM(credits) credits,
       SUM(cost_usd) usd
FROM usage_daily
WHERE day >= ?  -- date('now','-371 day')
  AND day <= ?
GROUP BY day ORDER BY day
```

窗口公式直接抄 `heatmap.go:29-32`；「只列有调用的天」抄 `:44-45`；「53 周」常量抄 `:21`。前端可直接复用 `Checkin.vue:322-420` 的日历网格骨架（已有骨架屏 + 图例 + tooltip + 月份表头），把「签到状态」换成「用量强度」，是**最低成本的热力图**。

### 建议 5（effort，P1-4）

`effort` 的落库和会话聚合一样，是「加一列」的事：

- 采集：`internal/gateway/dispatch.go:1365-1371`（`DefaultReasoning(snap, decision, hasReasoning)` 写入 `top["reasoning_effort"]`）——这里已经知道档位，顺手存进 `rec.effort`；
- 落库：`api_logs.effort TEXT`；
- 汇总：`usage_daily` 的 PK 若加 `effort` 会与现有 rollup 的 `ON CONFLICT(day,plugin_id,account_id,model)`（`internal/store/usage.go:669`）冲突，需一并改 PK 与 upsert，**成本比 api_logs 高**。建议第一期只在 `api_logs` 落、由前端按需求聚合，不动 `usage_daily`。

### 建议 6（价格引擎，P0-3）

aiworkgate 没有任何价格表，这是最大的一块新增。最小可用形态：

1. 新表 `model_prices(plugin_id, model, price_in, price_out, price_cache_read, price_cache_write_5m, price_cache_write_1h, currency, effective_from)`；
2. 在 `RollUsage`（`internal/store/usage.go:580-690`）算 `cost_usd` 写进 `usage_daily`，或在读时算（前者省查询、后者能改价回算——magpie 选的是「读时按当前价算 + `pricedAs` 记录当时按谁算」，更灵活）；
3. 无价的行保持 `NULL` 并在 UI 显示「无价」，**绝不要写成 0**（`usage_analytics.go:42-46` 的 `Credits *float64` 注释就是同一个教训）。

### 建议 7（P1-7 是本周就能做的）

`internal/usage/service.go:28-35` 的 `SummaryKPI` 加三个字段：

```go
AvgLatencyMS int64 `json:"avg_latency_ms,omitempty"`
AvgTTFBMS    int64 `json:"avg_ttfb_ms,omitempty"`
TTFBSamples  int64 `json:"ttfb_samples,omitempty"`
```

在 `:118-125` 里用 `totals.LatencyMSSum / totals.Requests` 与 `totals.TTFBMSSum / totals.TTFBCount`（注意 `TTFBCount==0` 时不要除）。前端 `Usage.vue:927-975` 加两格。**零新数据、零迁移。**
`Usage.vue:949` 的空态文案「平台未上报每请求积分」与这条同理：先把「有数据但没透出」清干净，再谈新采集。

### 建议 8（P1-8 一致性提示）

在 `Usage.vue` 的 `sessions` tab 头部（`:1538-1540`）与 `Logs.vue` 的请求日志 tab 加一行：

```
会话明细只覆盖请求日志保留期（默认 30 天），汇总数据覆盖 366 天。
```

数据来源：`config.Retention.APIRequestDays`（`internal/config/config.go:174`、默认 30 在 `:30`）+ `usage.MaxRangeDays`（`internal/usage/query.go:19`）。这是**文案级**修复，但能消掉「数据丢了」的误报。

### 优先级建议


## 18. 一句话结论

magpie 的用量层是「**一条调用 62 列的账本 + 五维份额 + 三层缓存 + 冷热分段落盘**」，把「请求的 / 发出的 / 应答的模型」「缓存读 / 写 / 1h / 未知」「时间花在哪（own/retried/queued/masking/flow）」「思考档」「窗口占用」都当一等公民；aiworkgate 的用量层是「**一条调用 24 列的日志 + 日聚合表 + 6 个展示视图**」，强在**延迟分位**与**多源实时时间线**，弱在**模型三栏、缓存写侧、价格**这三处——恰好是对账与成本最要命的三处。

先做 P0 三件套（一次迁移打包），再补 `Holds`/热力图/会话聚合，最后才谈价格引擎的完整形态。**`P1-7`（把已算好的延迟透出）是本周就能完成的最高性价比动作。**
