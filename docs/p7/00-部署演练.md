# P7 部署演练（Linux 服务器 + Caddy）

前置产物：`scripts/build-linux.sh`、`scripts/deploy-linux.sh`、`scripts/rollback-linux.sh`、`docs/p5/`（systemd/Caddy 样例）、`docs/p14/`（`/me` 页）。

> 本文是演练清单，不是已完成的部署记录。服务器、域名与安全前置未提供，因此**P7 验收尚未执行**；本地已完成的部分：交叉编译、部署/回滚脚本、dry-run 与文档。

## 0. 用户侧前置（阻塞 P7）

- [ ] 服务器（Ubuntu 22.04+，x86_64 或 arm64）+ 公网 IP
- [ ] 域名与 DNS A/AAAA 记录
- [ ] SSH 仅密钥、禁 root 密码；安全组只放 80/443（S-1/S-2）
- [ ] 宿主访问公网所需的代理/出口（按需）
- [ ] 已轮换曾暴露的令牌（githubToken 等）

## 1. 构建（开发机）

```bash
cd web && npm run build && cd ..
VERSION=0.1.0 bash scripts/build-linux.sh        # ARM 服务器：ARCH=arm64
```

检查点：`build/linux-amd64/aiworkgate` 存在，`SHA256SUMS` 已打印。

## 2. 安装与配置（服务器）

按 `docs/p5/00-公网部署与反代.md`：

- [ ] `/opt/aiworkgate/aiworkgate` + `aiworkgate` 系统用户 + `/var/lib/aiworkgate`
- [ ] `/etc/aiworkgate/env`（0600）：`AIWORKGATE_ADMIN_TOKEN`（≥32 字符）
- [ ] `/etc/systemd/system/aiworkgate.service`（样例见 `docs/p5/`）
- [ ] `/etc/caddy/Caddyfile`（样例见 `docs/p5/Caddyfile.example`：公网只放行 `/v1/* /me/* /healthz`）

## 3. 首次启动与网关设置

```bash
sudo systemctl enable --now aiworkgate
journalctl -u aiworkgate -n 100 --no-pager
ssh -L 7865:127.0.0.1:7865 user@server   # 本地打开 http://127.0.0.1:7865/?t=<token>
```

管理页里逐项确认：

- [ ] 对外域名 `public_hosts` = 你的域名（否则反代请求 403 invalid host header）
- [ ] 信任的反向代理 = `127.0.0.1`
- [ ] 允许访问 `/v1` 的来源 IP = 真实客户端网段（公网开放可 `0.0.0.0/0`，鉴权仍靠 Key）
- [ ] 服务模式 = `open`；按需设置每 Key / 每 IP 每分钟上限
- [ ] 创建客户端 Key（分享给他人的 Key 请设到期；whitelist 模式需勾「属主 Key」）
- [ ] 显式确认启用项：`redact.enabled`（正文脱敏）、`plugins.strict_egress`（出口白名单严格模式）、`rate_limit_per_minute` / `rate_limit_per_ip_per_minute`、`plugins.sandbox_user`——默认关闭，公网部署前逐项决策并勾选

## 4. 部署与回滚脚本

```bash
# 部署（dry-run 先看命令）
bash scripts/deploy-linux.sh user@server --dry-run
bash scripts/deploy-linux.sh user@server

# 回滚（部署失败或验收不过）
bash scripts/rollback-linux.sh user@server
```

脚本行为：旧二进制保留为 `/opt/aiworkgate/aiworkgate.prev`；上传到 `/tmp` 后**校验 SHA-256**再原子替换；`systemctl restart` 后轮询 `/healthz`，失败提示回滚。

## 5. 验收（P5/P7 对位）

```bash
# 无 Key → 401
curl -sS -o /dev/null -w '%{http_code}\n' https://<域名>/v1/models
# 带 Key → 200，列表含模型
curl -sS -H 'Authorization: Bearer <key>' https://<域名>/v1/models | head -c 400
# 管理面不对外
curl -sS -o /dev/null -w '%{http_code}\n' https://<域名>/api/status     # 期望 404
curl -sS -o /dev/null -w '%{http_code}\n' https://<域名>/              # 期望 404
# Key 自助页
curl -sS -o /dev/null -w '%{http_code}\n' https://<域名>/me/            # 期望 200
```

- [ ] HTTPS 证书正常；`/v1` 200、无 Key 401
- [ ] 伪造 `X-Forwarded-For` 的直连请求无法绕过 IP 白名单/限流
- [ ] 过期 Key → 401 含具体时间；停用 Key → 401
- [ ] `paused` → 503；`whitelist` 下非属主 Key → 403
- [ ] `/me/` 可登录、只显示自己的数据、无正文
- [ ] SSE 流式在 Caddy 下逐字到达（反代关闭缓冲；样例未显式开 buffering，若异常加 `flush_interval -1`）
- [ ] 回滚演练：手动部署坏二进制 → `rollback-linux.sh` → `/healthz` 恢复

## 6. 凭据轮换与吊销流程（S5-6）

对应安全计划 S-5-6「凭据轮换与吊销流程写进运维手册（谁、何时、怎么验）」与主线 D-09（一键吊销 + 吊销后本机重登）。

**谁**：仅管理员本人。客户端 Key 持有者无权触发任何凭据操作；凭据入口只有 SSH 隧道内的管理页（S-3：`/api` 不对外）。

**何时**（触发即做，不等季度节点）：

- 例行：每季度一次轮换演练（安全计划 §5「持续」清单）
- 异常：某渠道 `last_used_at` 出现在非活跃时段或出现陌生调用；上游平台公告泄露；更换部署机；某令牌曾以明文出现在任何位置（对照 D-17 的 githubToken 处置）

**怎么验**（按序执行）：

1. 本机重登渠道：管理页（SSH 隧道）「登录」→ 浏览器回调（仅本机，D-06）→ 新凭据落本机 `DATA_DIR`。
2. 推送到服务器：**（占位——凭据推送链路属 P4，尚未实现，P4 实现后启用：本机同步器读 magpie 登录态 → 加密 → 经 SSH 隧道推送到服务器凭据库。）**
3. 服务器侧一键吊销某个渠道：SSH 隧道进管理页 → 该渠道凭据 → 吊销 → 置 `revoked`，桥立即停用该渠道（D-09）。
4. 轮换后验证：

   ```bash
   curl -sS -o /dev/null -w '%{http_code}\n' https://<域名>/healthz                     # 期望 200
   curl -sS -H 'Authorization: Bearer <key>' https://<域名>/v1/models | head -c 200    # 期望 200，列表含该渠道模型
   ```

   - [ ] 管理页渠道列表显示新凭据状态正常，`last_used_at` 随首次调用更新
   - [ ] 吊销后的旧渠道请求立即失败（401 / 明确文案，`revoked` 后不可用）

## 7. 入侵应急流程（S7-7）

对应安全计划 S-7-⑦「断网 → 保全证据 → 吊销全部凭据 → 重建而非清理」。疑似入侵（异常登录、陌生进程、凭据库被读、面板漏洞被利用）时按序执行，**顺序不能倒：先止血再取证**。

**① 断网（先做）**

- 云控制台把安全组入站改为全部拒绝；如需保留取证 SSH，把 22 端口来源收紧到当前出口 IP。
- 服务器上兜底（重启失效，仅作临时止血）：`sudo ufw default deny incoming`

**② 保全（先于任何重启/清理，证据重启即失）**

```bash
D=/root/incident-$(date +%Y%m%d-%H%M); mkdir -p $D
ps auxf > $D/ps.txt; ss -tlnpu > $D/ss.txt
journalctl --no-pager > $D/journalctl.txt
cp -a /var/log/auth.log /var/log/audit/ $D/ 2>/dev/null
last -f /var/log/wtmp > $D/wtmp.txt; lastb > $D/lastb.txt 2>/dev/null
sudo cp -a /var/lib/aiworkgate/.config/AIWorkGate $D/aiworkgate-data   # 凭据库 + secrets + DB 原样快照
sudo tar czf $D/snapshot.tgz -C $D . && sha256sum $D/snapshot.tgz
```

- [ ] 快照另存一份到本机（`scp` 拉回）；不要上传到不可信的网盘/仓库

**③ 吊销（堵住额度面与冒用面）**

- 停用全部客户端 Key：管理页逐个停用；管理面已不可信时直接 `systemctl stop aiworkgate`（`/v1` 全部随之下线）。
- 重置服务器凭据：服务器凭据库视为已失守，`revoked` 标记只对内有效——**必须到各上游平台（trae/workbuddy/codebuddy 等）强制下线全部会话/改密**，让被拷走的 refresh token 真正作废。

**④ 重建（不清理，重装）**

- 重装系统（不在被入侵的磁盘上做「杀进程了事」的清理）。
- 按 P7 演练重部署：先过 §8 安全验收清单（S-1/S-2/S-7 逐项），再走 §1 构建 → §2 安装配置 → §3 首次启动。
- 从本机重推凭据：本机重登受影响渠道（D-09「吊销后本机重登即可」）→ 推送到新服务器（推送链路未实现，P4 实现后启用）。

**⑤ 复盘**

- 用 ② 的证据确认入侵路径，写入变更日志；据此决定是否把安全计划的某条加固提前。

## 8. 服务器侧安全验收清单（S-1/S-2/S-7）

把安全计划的服务器侧要求逐条落成可勾选步骤（出处：[安全加固计划](../../plans/2026-11-05-安全加固计划.md) S-1/S-2/S-7 与 §5 加固清单）。
S-3 的 Caddy/WAF/SSE 部分不在此重复：TLS、`/api` 不对外、SSE 逐字到达已在 §5 验收覆盖；WAF 选型与雷池缓冲取舍见安全计划 S-3。

### S-1 网络入口

- [ ] 云安全组/UFW 默认拒绝入站，只放 80/443

  ```bash
  sudo ufw status verbose    # 期望：deny (incoming)，仅 80/443（SSH 白名单见 S-2）
  ```

- [ ] 除回环外无多余监听；aiworkgate 只绑 `127.0.0.1`（`listen_lan=false`）

  ```bash
  ss -tlnp | grep -v 127.0.0.1    # 期望：只剩 80/443（Caddy）
  ss -tlnp | grep 7865            # 期望：127.0.0.1:7865
  ```

- [ ] 外网扫描复核（从另一台机器执行；一次性低频扫描，绝不对生产压测）

  ```bash
  nmap -Pn -p- <公网IP>           # 期望：只见 80/443
  ```

### S-2 SSH

- [ ] 禁密码 / 禁 root / `MaxAuthTries 3` / `AllowUsers <deploy-user>`（`/etc/ssh/sshd_config`）

  ```bash
  sudo sshd -T | grep -E 'passwordauthentication|permitrootlogin|maxauthtries|allowusers'
  # 期望：passwordauthentication no / permitrootlogin no / maxauthtries 3 / 仅部署用户
  ```

- [ ] fail2ban 已安装且 sshd jail 生效

  ```bash
  sudo systemctl is-active fail2ban
  sudo fail2ban-client status sshd    # 期望：jail 在列且有匹配/封禁统计
  ```
