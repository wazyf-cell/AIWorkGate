## 2.5 桥插件（bridge-<渠道>）落盘与凭据注入

> task-86/89 调研固化（2026-11-09）。服务器上 7 个 bridge-* 插件的目录布局、命名与凭据注入路径如下；
> 前提：Linux 桥 binary 已交叉编译（ELF64，sha256 见 dist/ 哈希记录文件）。

**1. Linux 插件目录在哪**。DataDir 解析：Windows 用 `%APPDATA%\AIWorkGate`，Linux 走 `os.UserConfigDir()`（`internal/config/file.go:16-23`）；systemd 单元设 `Environment=HOME=/var/lib/aiworkgate`（`docs/p5/aiworkgate.service.example:17`），因此服务器实际 DataDir = **`/var/lib/aiworkgate/.config/AIWorkGate`**。插件目录 = `<DataDir>/plugins`（`internal/plugins/manager.go:218`），即 `/var/lib/aiworkgate/.config/AIWorkGate/plugins/bridge-<id>`；p7 §7 入侵快照命令 `cp -a /var/lib/aiworkgate/.config/AIWorkGate` 印证同一形态。不是 `/opt`、不是独立 XDG 变量——由 systemd 的 HOME 决定。

**2. 每个渠道落盘三件**（对照 `scripts/install-bridge-plugin.ps1:92-155` 的动作清单，服务器侧按同名内容手工/bash 化执行）：① magpie 插件包只读拷贝（`index.mjs` 等，源 `~/.config/magpie/plugins/node_modules/@magpie-community/opencode-<渠道>-auth`，脚本 `:33`）→ `<DataDir>/plugins/bridge-<id>/`；② Linux 桥 binary；③ golden 形状 `manifest.json`（`id=bridge-<id>`、`api_level=1`、`capabilities=[upstream,accounts,checkin]`、`network_domains` 从 `index.mjs` 的 `https://` 引用自动枚举并补 `*.<host>`，脚本 `:78-90/:144-145`）。

**3. entry.exe 跨平台命名决策**。契约要求 entry.exe 相对插件目录（supervisor 以 `filepath.Join(pluginDir, entry.exe)` 解析，`internal/opchost/bridge.go:92-94`；绝对路径与 `..` 逃逸被 `:138-157` 拒绝），且共享桥默认名是常量 `DefaultBridgeExeName = "magpie-bridge.exe"`（`bridge.go:17`）。**决策：Linux 产物（如 `dist/magpie-bridge-linux`）部署时改名为 `magpie-bridge.exe` 落进插件目录**——Linux 文件名带 `.exe` 完全合法，manifest 与 Windows 逐字节一致、golden 脚本零分叉；改名方案会与 Windows manifest 分叉，不取。

**4. `--plugin-dir` 与完整性**。manifest 的 `entry.args` 只有 `["--plugin-dir", <插件目录绝对路径>]`（`bridge.go:81-83` BridgeArgs 原样写入），必须写成**服务器上的绝对路径**（如 `/var/lib/aiworkgate/.config/AIWorkGate/plugins/bridge-trae`），不得复用本机预览路径（预览 manifest 实测指向 `runtime/preview-appdata`）。落盘前 `sha256sum -c` 对 dist 哈希记录（`dist/magpie-bridge.sha256` / `dist/magpie-bridge-linux.sha256`）校验 ELF。

**5. 重启与生效**。落盘后 `systemctl restart aiworkgate`（或等宿主下一次 Discover，`internal/plugins/manager.go:286` 扫描 `<DataDir>/plugins`），宿主在 `/api/status` 与管理页出现 bridge-<id>；本安装动作不重启宿主（`scripts/install-bridge-plugin.ps1:20`）。

**6. 凭据注入**。桥凭据库 = `<DataDir>/plugin-data/bridge-<id>/credentials.json`（AES-256-GCM + `bridge.key` 0600），由 `AIWORKGATE_PLUGIN_DATA_DIR` 指定（supervisor 注入，`internal/plugins/env.go:29` + `internal/plugins/manager.go:229-234`；**凭据不进环境变量**，`internal/plugins/env.go:59-60`）。服务器没有本机的 `~/.config/magpie/plugin-auth.json`，桥启动时自动导入不可用。注入通道：**当前形态 = SSH 隧道内经宿主 `/api/status` 读出桥的动态端口与插件 token，直连桥 `POST /admin/credentials`**（端点全家桶 `opchost/bridge/src/admin/router.ts:128-161`；响应纯脱敏不含指纹/明文，`opchost/bridge/src/admin/credentials.ts:8`）——即 P1 设计的「/admin/credentials 注入，服务器用」。宿主 P4 库（`<DataDir>/secrets.dat` 的 `credential.<plugin>.<account>` 键位，`internal/app/credential_sync.go:24-28/:126`）与桥凭据库目前**相互独立**；宿主代转端点正在实现（task-90），落地后本条更新为「P4 推送后由宿主代转各桥」。

**7. plugin-data 幂等铁律**。已存在的 `bridge-<id>/` 只同步 exe 与 manifest，**永不触碰** `plugin-data/<id>` 的 credentials.json 等凭据（`scripts/install-bridge-plugin.ps1:7-8/:102/:158-164`）；服务器重装/换 binary 时同样只换 exe 与 manifest。

**8. UNKNOWN（需实机验证）**：① Linux bun 产物未实机跑过（交叉编译成功 ≠ 运行成功）；② 7 渠道的 `network_domains` 枚举未在 Linux 侧实测（本机脚本已产出过 trae 11 域）；③ 桥在 Linux 的凭据加密路径（`bridge.key` AES-256-GCM 本就跨平台，风险低但未实测）。

**用户必须提供的 6 项服务器信息**（对照 §0）：① OS 与架构（Ubuntu 22.04+，x86_64 或 arm64 → 决定 `ARCH`）；② SSH 访问 `user@host`（密钥已配；部署与凭据同步共用此通道）；③ 域名 + DNS A/AAAA 已指向服务器（Caddy 自动证书前提）；④ 云安全组可控（只放 80/443）；⑤ 服务器出口是否需要代理访问上游渠道（GitHub 曾不可达，F-04）；⑥ 确认 githubToken 随 P4 推送（D-17 裁决：复用，加密存储）。

## 5. 验收（P5/P7 对位）

```bash
# 无 Key → 401
curl -sS -o /dev/null -w '%{http_code}\n' https://<域名>/v1/models
# 带 Key → 200，列表含模型
curl -sS -H 'Authorization: Bearer <key>' https://<域名>/v1/models | head -c 400
# 管理面不对外

# Key 自助页
curl -sS -o /dev/null -w '%{http_code}\n' https://<域名>/me/            # 期望 200
```

- [ ] 伪造 `X-Forwarded-For` 的直连请求无法绕过 IP 白名单/限流
- [ ] 过期 Key → 401 含具体时间；停用 Key → 401
- [ ] `paused` → 503；`whitelist` 下非属主 Key → 403
- [ ] `/me/` 可登录、只显示自己的数据、无正文
- [ ] SSE 流式在 Caddy 下逐字到达（反代关闭缓冲；样例未显式开 buffering，若异常加 `flush_interval -1`）

## 6. 凭据轮换与吊销流程（S5-6）

对应安全计划 S-5-6「凭据轮换与吊销流程写进运维手册（谁、何时、怎么验）」与主线 D-09（一键吊销 + 吊销后本机重登）。

**谁**：仅管理员本人。客户端 Key 持有者无权触发任何凭据操作；凭据入口只有 SSH 隧道内的管理页（S-3：`/api` 不对外）。

**何时**（触发即做，不等季度节点）：

- 例行：每季度一次轮换演练（安全计划 §5「持续」清单）
- 异常：某渠道 `last_used_at` 出现在非活跃时段或出现陌生调用；上游平台公告泄露；更换部署机；某令牌曾以明文出现在任何位置（对照 D-17 的 githubToken 处置）

**怎么验**（按序执行）：

1. 本机重登渠道：管理页（SSH 隧道）「登录」→ 浏览器回调（仅本机，D-06）→ 新凭据落本机 `DATA_DIR`。
2. 推送到服务器：**（占位——凭据推送链路属 P4，尚未实现，P4 实现后启用：本机同步器读 magpie 登录态 → 加密 → 经 SSH 隧道推送到服务器凭据库。）**
3. 服务器侧一键吊销某个渠道：SSH 隧道进管理页 → 该渠道凭据 → 吊销 → 置 `revoked`，桥立即停用该渠道（D-09）。
4. 轮换后验证：

   ```bash
   curl -sS -o /dev/null -w '%{http_code}\n' https://<域名>/healthz                     # 期望 200
   curl -sS -H 'Authorization: Bearer <key>' https://<域名>/v1/models | head -c 200    # 期望 200，列表含该渠道模型
   ```

   - [ ] 管理页渠道列表显示新凭据状态正常，`last_used_at` 随首次调用更新
   - [ ] 吊销后的旧渠道请求立即失败（401 / 明确文案，`revoked` 后不可用）

## 7. 入侵应急流程（S7-7）

对应安全计划 S-7-⑦「断网 → 保全证据 → 吊销全部凭据 → 重建而非清理」。疑似入侵（异常登录、陌生进程、凭据库被读、面板漏洞被利用）时按序执行，**顺序不能倒：先止血再取证**。

**① 断网（先做）**

- 云控制台把安全组入站改为全部拒绝；如需保留取证 SSH，把 22 端口来源收紧到当前出口 IP。
- 服务器上兜底（重启失效，仅作临时止血）：`sudo ufw default deny incoming`

**② 保全（先于任何重启/清理，证据重启即失）**

```bash
D=/root/incident-$(date +%Y%m%d-%H%M); mkdir -p $D
ps auxf > $D/ps.txt; ss -tlnpu > $D/ss.txt
journalctl --no-pager > $D/journalctl.txt
cp -a /var/log/auth.log /var/log/audit/ $D/ 2>/dev/null
last -f /var/log/wtmp > $D/wtmp.txt; lastb > $D/lastb.txt 2>/dev/null
sudo cp -a /var/lib/aiworkgate/.config/AIWorkGate $D/aiworkgate-data   # 凭据库 + secrets + DB 原样快照
sudo tar czf $D/snapshot.tgz -C $D . && sha256sum $D/snapshot.tgz
```

- [ ] 快照另存一份到本机（`scp` 拉回）；不要上传到不可信的网盘/仓库

**③ 吊销（堵住额度面与冒用面）**

- 停用全部客户端 Key：管理页逐个停用；管理面已不可信时直接 `systemctl stop aiworkgate`（`/v1` 全部随之下线）。
- 重置服务器凭据：服务器凭据库视为已失守，`revoked` 标记只对内有效——**必须到各上游平台（trae/workbuddy/codebuddy 等）强制下线全部会话/改密**，让被拷走的 refresh token 真正作废。

**④ 重建（不清理，重装）**

- 重装系统（不在被入侵的磁盘上做「杀进程了事」的清理）。
- 按 P7 演练重部署：先过 §8 安全验收清单（S-1/S-2/S-7 逐项），再走 §1 构建 → §2 安装配置 → §3 首次启动。
- 从本机重推凭据：本机重登受影响渠道（D-09「吊销后本机重登即可」）→ 推送到新服务器（推送链路未实现，P4 实现后启用）。

**⑤ 复盘**

- 用 ② 的证据确认入侵路径，写入变更日志；据此决定是否把安全计划的某条加固提前。
