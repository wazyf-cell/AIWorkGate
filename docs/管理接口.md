# 管理接口一览（谁在调用）

> 这份文档回答一个问题：`/api/*` 里每条路由**有没有 UI 调用方**，没有的话为什么还留着。
> 认证与防护：只监听回环（或显式开启的局域网地址），所有 `/api/*` 都要先换 `POST /api/session` 的会话 Cookie；带副作用的请求还要求同源（Origin / Sec-Fetch-Site）检查。密钥、密码、Cookie 明文不落盘、不回显。
> 错误包封：`{"error":{"message":"…","type":"…","code":"…"}}`。`type` 是机器可读分类，`code` 在 API 面（尤其 `/v1`）保持与 OpenAI 一致。

## 1. 有 UI 调用方的路由

判断标准：`web/src/api.ts` 里有对应方法，且该方法在 `web/src/views` 或 `web/src/App.vue` 被调用。按页面归类（不是每个端点都列，参数化路由合并成一行）：

| 页面 / 模块 | 路由 |
|---|---|
| 外壳 | `GET /api/status`、`POST /api/session` |
| 概览 | 复用状态与日志接口 |
| 插件 | `GET /api/plugins`、`POST /api/plugins/install`、`/api/plugins/{id}/{action}`（enable/disable/start/stop/uninstall）、`GET /api/plugins/{id}/meta`、`GET|PUT /api/plugins/{id}/settings` |
| 账号 | `GET /api/accounts`、`POST /api/accounts/save|patch|delete|refresh|checkin|bulk|login|login/{sid}/submit`、`GET /api/accounts/login-state`、`POST /api/accounts/identity/details|identity/reset`、`GET|POST /api/groups` |
| 签到 | `GET /api/checkin`、`POST /api/checkin/all` |
| 规则 | `GET|PUT|DELETE /api/rules`、`/api/rules/{name}`、`POST /api/rules/{name}/reset`、`POST /api/rules/reload` |
| 代理 | `GET|POST|PUT|DELETE /api/proxies`、`/api/proxies/{id}`、`POST /api/proxies/{id}/check`。保留行 `id=system` 由宿主跟随 Windows 设置自动维护：列表里带 `managed:"system"`、`managed_detail`（未启用原因）；对它 `POST/PUT/DELETE` 返回 **409 `managed_proxy`**，`check` 仍可用来测当前出口 |
| 日志 | `GET /api/logs/requests`、`/api/logs/requests/export`、`/api/logs/timeline`、`/api/logs/proxy`、`/api/logs/raw`、`/api/logs/body`、`/api/logs/stream`（EventSource）。`/api/logs/timeline` 用游标翻页：`page_size` + `cursor`（取上一页的 `next_cursor`），响应 `has_more` / `next_cursor`；`page` 参数已删除，传 `page>1` 返回 400 |
| 用量 | `GET /api/usage/summary|credits|expiry|sessions|export|latency|latency/models|keys|models` |
| Key / 自定义模型 | `GET|POST|DELETE /api/keys`、`/api/keys/{id}`、`/api/custom-models`、`/api/custom-models/{id}`、`POST /api/custom-models/{id}/test`、`/api/custom-connections`（含 `/test`、`/remote-models`、`/models/import`） |

| 调度 | `GET /api/scheduler`、`PUT /api/scheduler/global`、`PUT /api/scheduler/pools/{plugin}`、`POST /api/scheduler/presets/{name}`、`PUT|DELETE /api/scheduler/models/{logical}`、`POST /api/scheduler/explain`、`GET|DELETE /api/scheduler/sticky` |

| 设置 | `GET|PUT /api/settings`、`GET|PUT /api/secrets/a-key`、`/api/secrets/lan-password`、`GET|PUT|POST /api/notify`、`POST /api/notify/test` |

## 2. 保留但没有 UI 调用方的接口（运维 / 脚本）

这 5 条在 `web/src/api.ts` 里有类型化封装，但页面没有使用。保留原因是运维脚本和历史验收流程依赖它们；**语义与表格里对应的 UI 路径一致**，不要另立第二套写入方式。

| 路由 | 用途 | 为什么 UI 不用它 | 报文 |
|---|---|---|---|
| `PUT /api/accounts/egress` | 给某个账号绑定/解绑出口代理，并让插件重载 | 账号页的草稿保存（`POST /api/accounts/save`）在同一个事务里写 `egress`，避免两次写 | `{plugin_id, account_id, mode: "direct"|"proxy"|"blocked", proxy_id?}` → `{ok, reloaded}` |
| `POST /api/accounts/rename` | 只改宿主别名覆盖层（对全部插件生效） | 账号页把别名和其它字段一起走 `POST /api/accounts/save` | `{plugin_id, account_id, alias}` |
| `GET /api/pools/{plugin}/catalog` | 单独读某个插件的模型目录 | 资源详情页一次 `GET /api/pools/{plugin}` 就带回 `catalog` | 只读 |
| `GET /api/scheduler/models` | 单独读逻辑模型绑定表 | 调度页一次 `GET /api/scheduler` 就带回 `models` | 只读 |
| `GET /api/logs/runtime?source=&n=` | 读宿主/插件 JSONL 的原始条目 | 日志页的「运行」分类走 `GET /api/logs/timeline`（已合并来源、分页与筛选） | 只读 |

> 这些接口和 UI 路径**写的是同一份存储**，没有第二套语义。脚本用它们不会和页面打架。

## 3. 已删除的路由（不要再加回来）

| 路由 | 删除原因 |
|---|---|
| `PUT /api/groups/{id}`、`DELETE /api/groups/{id}`、`PUT /api/groups/{id}/members` | 分组改名、删除、换成员已经由 `POST /api/accounts/save` 的 `groups` / `deleted_groups` 在一次事务里完成；两套写入口容易改错一边。分组**创建**仍用 `POST /api/groups`（新分组要先有 id，账号草稿才能引用）。 |
| `GET /api/accounts/{id}/history` | 签到回填历史从未有插件实现（能力表里也没有 `history`），声明该能力会触发“未知能力”告警。历史记录统一看 `GET /api/checkin`。 |

## 4. 新增路由时的规矩

1. 先决定调用方：页面用，还是脚本/运维用。页面用就在 `api.ts` 加类型化方法并在视图里调用；脚本用就在 §2 登记一行。
2. 同一份数据只保留一条**写**路径。只读接口可以多，写接口不行——宁可让脚本调用 UI 的写入口，也不要新增“只给脚本用的第二条写路径”。
3. 参数化路由的校验必须在 transport 层做完再进业务回调（现有实现如此），并补一条 400 用例。
